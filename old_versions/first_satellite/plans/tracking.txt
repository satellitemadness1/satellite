satellite — real header dependency tracking
===========================================
Written 2026-08-24. Subject: the Makefile's $(OBJS): $(HDRS) rule.

Written to survive a /clear: everything needed to carry this out is in this
file, including the line numbers as they stand today and what to check
afterwards. References to the design are by section number, never by line.


THE PROBLEM, AND IT IS TWO PROBLEMS
-----------------------------------
Makefile:702 is one line:

    $(OBJS): $(HDRS) .cxxflags-stamp

$(OBJS) is 44 objects. $(HDRS) (Makefile:337-344) is 17 headers. So the build
declares an all-to-all dependency: touching ANY of the seventeen recompiles ALL
forty-four. That is why editing src/satellite_value/value.hpp -- which four
objects actually include -- costs a full rebuild, and it is the whole of the
complaint this plan answers.

TOO COARSE is the half everybody notices. The other half is the reverse and it
is worse:

TOO NARROW. $(HDRS) is a HAND-WRITTEN list, and a header that is not on it is a
header no object depends on at all. The Makefile already says so in its own
comments, twice:

  - version.hpp is deliberately excluded, and three recipes name it by hand
    instead (Makefile:345-349, and the recipes at 620, 627, 640).
  - format.hpp/format.def is deliberately excluded, and the comment at the top
    of format.def records what that cost: "version.hpp was in no rule at all,
    so editing it rebuilt nothing", which the notes call "format.def's defect
    from §17".

A hand-written list has that failure mode permanently. Every header added from
here on is one somebody has to remember to add, and forgetting is silent: the
build succeeds and links a stale object. -MMD ends that class of bug for good,
because the compiler reports what it actually opened.

So this is a correctness change that happens to also be a speed change. Say it
that way in the commit message.


THE CHANGE
----------
Compiler-generated dependency files, one per object, beside the object.

    DEPFLAGS = -MMD -MP

-MMD writes `foo.o: foo.cpp a.hpp b.hpp ...` to foo.d as a side effect of the
compile that was happening anyway -- so it costs no extra pass. The second M is
what leaves SYSTEM headers out: <vector> never changes without the toolchain
changing, and .cxxflags-stamp already catches a changed compiler.

-MP IS NOT OPTIONAL. It emits an empty phony target for each header listed.
Without it, deleting or renaming a header leaves a stale .d naming a file that
no longer exists, and the next make dies with

    No rule to make target 'src/.../old.hpp', needed by 'src/.../x.o'

which is a build that cannot be fixed except by hand-deleting .d files. src/
was reorganised into per-module directories once already (commit f63460d); it
will happen again.

    STEP 1. DEPFLAGS ON EVERY COMPILE RECIPE, AS A LITERAL.

DEPFLAGS goes on the recipe lines, NOT into CXXFLAGS. This is the same argument
Makefile:614-624 already makes for -I$(SRC), and it is load-bearing for the
same reason: `make CXXFLAGS=...` replaces that variable WHOLE, and debian/rules
does exactly that. A flag the build's correctness depends on must not be
droppable by an override. Put it beside -I$(SRC) on all five recipes:

    Makefile:625   $(SRC)/%.o: $(SRC)/%.cpp          the pattern rule, 40 objects
    Makefile:620   $(PROGRAMS)/main.o                VERSION_DEFS
    Makefile:627   $(EVAL)/help.o                    VERSION_DEFS
    Makefile:640   $(PROGRAMS)/window.o              gtk, VERSION_DEFS
    Makefile:697   $(SYSTEM)/system.o                SATELLITE_LIB_DIR

    STEP 2. REPLACE THE BLANKET RULE.

    Makefile:702    $(OBJS): $(HDRS) .cxxflags-stamp
    becomes         $(OBJS): .cxxflags-stamp

KEEP THE STAMP. .cxxflags-stamp and .libdir-stamp are not header dependencies
and no compiler can report them -- they are configuration, and they exist so
that changing OPT or CXX or the prefix rebuilds what was told the old value.
A depfile knows nothing about either. Removing them here would be trading one
correctness bug for another.

$(HDRS) itself stays defined: Makefile:711 (library_test_tsan) still uses it,
and it is the honest fallback for anything that has never been compiled.

    STEP 3. INCLUDE THE DEPFILES.

Below the rules, near the bottom:

    DEPS = $(OBJS:.o=.d) $(PROGRAMS)/window.d
    -include $(DEPS)

`-include` and not `include`: on a clean tree there are no .d files yet, and
the leading dash is what makes their absence silent rather than fatal. That is
also why the first build after `make clean` is correct without them -- there is
no object to be stale.

window.o is named separately because it is not in $(OBJS) (satl-term links it
alone, Makefile:609).

    STEP 4. THE TEST BINARIES, WHICH ARE UNDER-SPECIFIED TODAY.

Thirty recipes of this shape (Makefile:727 and its neighbours):

    $(EVAL)/eval_test: $(EVAL)/eval_test.cpp $(LIBOBJS)
        $(CXX) $(TESTFLAGS) -I$(SRC) $(OPT) -o $@ $(EVAL)/eval_test.cpp $(LIBOBJS)

They compile straight to a binary with no .o in between, and they list NO
headers -- so editing eval.hpp does not rebuild eval_test. It happens to be
caught today because $(LIBOBJS) rebuilds and relinks it, and that is luck
rather than a rule: it would not catch a header only the test itself includes.

Give them their own depfile, named off the binary since there is no object:

    -MMD -MP -MF $@.d

and add

    -include $(TESTBINS:=.d)

Do this in the same pass. It is the same defect and doing it twice is worse.

    STEP 5. CLEAN AND GITIGNORE.

    Makefile:1136   add $(SRC)/*/*.d and $(TESTBINS:=.d) to the rm -f list
    .gitignore:49   add *.d beside *.o and *.o.tmp

A build product that survives `make clean` is a build product that ends up in
somebody's tarball -- the Makefile's own words at 1138.

    STEP 6. RETIRE THE HAND-WRITTEN version.hpp PREREQUISITES -- LAST, AND ONLY
    AFTER PROVING THE DEPFILES CARRY THEM.

The three recipes at 620, 627 and 640 name $(SYSTEM)/version.hpp by hand. Once
depfiles work that is redundant, and two mechanisms saying the same thing is
the drift this repository keeps warning about. But REMOVE IT ONLY AFTER the
check below passes with it already removed -- prove the .d file carries it,
then delete the belt. If in doubt, leave them: redundant is not wrong.


HOW TO KNOW IT WORKED
---------------------
Measure BEFORE changing anything, or there is nothing to compare against.

    STEP 0 (do this first, before any edit):
        make clean && time make satl SATELLITE_AUTOINSTALL=0
    Record the wall time and that it compiled 44 objects.

Then, after the change, each of these is a separate check and each has an
expected number. Count with:

        touch <header> && make satl SATELLITE_AUTOINSTALL=0 -n | grep -c ' -c -o '

  a. touch src/satellite_value/value.hpp     -> the objects that include it,
                                                NOT 44. This is the headline.
  b. touch src/satellite_number/bignum_internal.hpp -> a handful.
  c. touch src/system_facts/version.hpp      -> exactly 3 (main, help, window).
                                                Today that is true only because
                                                three recipes say so by hand;
                                                after this it is true because
                                                the compiler said so.
  d. touch src/bytecode_format/format.def    -> NOT ZERO. Today it is zero, and
                                                that is the defect format.def's
                                                own header describes. This is
                                                the check that proves the
                                                correctness half.
  e. touch src/evaluator/eval.hpp            -> eval_test relinks (step 4).
  f. make with nothing touched               -> 0 compiles, twice running.
                                                The fixed point must survive.

  g. make clean && make                      -> full build from scratch, clean.
  h. make test                               -> all sixteen binaries, zero
                                                failures. Baseline today is 14
                                                PASS lines plus the TSAN build.
  i. make CXXFLAGS='-std=c++20 -O2' satl     -> MUST still build. This is the
                                                debian/rules path, and it is
                                                the one that breaks if DEPFLAGS
                                                went into CXXFLAGS instead of
                                                onto the recipes.
  j. rename a header, make                   -> must NOT die with "No rule to
                                                make target". This is -MP.
                                                Rename it back afterwards.

Write the measured numbers from (a) and (g) into the commit message. "Rebuilds
4 objects instead of 44" is the sentence this change exists to be able to say.


NOT IN THIS PLAN
----------------
PARALLELISM. `make -j24` is a bigger win than this on a 24-thread machine and
needs no edit at all -- but it must NOT be baked into the Makefile with
MAKEFLAGS += -j. A packager drives this file (debian/rules through
dh_auto_build) and chooses its own job count; a hard-coded -j fights it, and on
a build machine with other work it oversubscribes. It belongs in BUILDING.md as
advice, which is a separate, one-paragraph change.

The two compose: depfiles cut WHAT is rebuilt, -j cuts how long what remains
takes.

ccache. Helps most when flipping between branches or between -O2 and -O3.
Orthogonal to this, and not needed to make the edit-compile loop fast.
