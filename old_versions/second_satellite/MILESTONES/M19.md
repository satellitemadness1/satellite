# M19 — persistence: files and directories

**Landed 2026-09-08** (`71f0e6a`).

[PLAN.md](../PLAN.md) §8's M19 entry is the specification. Its demand is two
programs under `satl --run`: a round trip over every path that **leaves the tree
as it found it**, and QUAD's corpus reader written in satellite by hand, whose
two counts must match the C++ QUAD's on the same file.

This is a **review and not a plan**: what was decided on the way, what building
it found, and what it left open.

    $ satl example/persistence.satl
    the reason: No such file or directory
    PASS

    $ satl example/persistence.satl        # and again, and again
    the reason: No such file or directory
    PASS

    $ satl example/corpus_reader.satl      # 1029 lines of QUAD's wiki corpus
    documents 114
    lines 915

    $ ./quad_reference corpus/wiki.txt     # quad_main.cpp:184-197, transcribed
    documents 114
    lines 915

    $ satl example/persistence_bad_mode.satl
    satl: example/persistence_bad_mode.satl:18:52: error S1201: `open` opens a
          file in one of four modes -- "read", "write", "append" or
          "read_append" -- and "binary" is not one of them

**Nine files under `src/satellite_file/` and `src/satellite_directory/`, five
under `tests/file_test/`, three example programs, and edits to twenty-two files
that already existed.** Five new word numbers, six call shapes written onto rows
that had none, eight new error codes, one new `Value` arm, and one small list
appended to `words.def`.

---

## 1. What the milestone was

- **Twenty paths that were numbered at M2 and reached by nothing since**, plus
  **five minted here** when the author settled the open items PLAN had been
  carrying since 2026-08-28. §2.1.
- **The file handle as the language's first reference type** — the only arm of
  `Value` that is not `const` behind its handle, and the first one where two
  names for a thing are one thing. §2.2.
- **A read cursor that is the language's and not the kernel's**, which is all
  M19 adds to v1's design and is forced by a sentence DESIGN wrote at M12. §2.3.
- **A fold that was guessing, and had been wrong in shipped code since M16.**
  Found by hitting it a second time. §2.4.
- **`+` joins two strings**, because M19's own diagnostics could not be written
  without it. §2.5.
- **A test that asserts which refusal**, because the half of this milestone that
  refuses cannot be checked by a program that runs. §3.

## 2. The decisions

### 2.1 Five numbers the author minted, and why the milestone could not start without three of them

**PLAN said the failed-open contract had no numbers and that this blocked the
demonstration, and it was right.** DESIGN §9 makes a failed open a **value** —
the handle comes back holding `errno` and the caller asks — and PLAN's own
done-when says *"open a path that does not exist, print the reason, and keep
running"*. There is no way to write that sentence without words for *did it
work* and *why not*, and WORD_NUMBERS §2.2 ran `1 6 2 1` through `1 6 2 7` and
stopped. The v1 sweep that built §2.2 missed all three of v1's own.

**The author settled it on 2026-09-08: `ok` `1 6 2 8`, `path` `1 6 2 9`,
`error` `1 6 2 10`.** v1's contract exactly, and **v1's handle `clear` does not
come across** — which is what settled `1 8 3` two rows down, because with no
handle spelling the module face is the only face and duplicates nothing.

**`write(x)` `1 6 2 11` is the fourth, and it is the shape of the question that
produced it.** PLAN framed `write_line(s)` `1 6 2 4` as a straight fight —
v1's `.write` deliberately appends no newline, on the grounds that a file with
no trailing newline and a line assembled from several calls both become
unwritable, against a word in the numbering that says `write_line`. **Asked
which wins, the author asked what a binary file does**, and the answer is that
satellite has no binary mode and one verb serves every file — so a `write_line`
that always appends would make raw bytes unwritable full stop. **Both verbs
exist and neither argument loses.**

**`satellite.file.exists(path)` `1 8 5` is the fifth.** `exists` `1 6 2 7` sits
on the type node, so §6.4 desugars it to a call binding a receiver — and *does
this file exist* is asked before a handle exists. Both rows are built and they
are two questions: `1 8 5` asks about a path, `1 6 2 7` asks whether **this
handle's own** path is still there, which is what the done-when's last clause
asks after a `satellite.system.delete`.

**And `satellite.variable.file.new` `1 6 2 1` is built by nothing, deliberately.**
PLAN asked for the reading to be confirmed and it is: DESIGN §6.4 qualification 2
names `my_file.new()` as the confusing arity error the receiver tag EXISTS TO
PREVENT, not as a spelling to build, and v1 has no `new` handle method at all.
A program writes `satellite.file.new(path)` `1 8 1`. `open` is **not** a second
collision of the same kind — `1 8 2` opens a path and `1 6 2 2` reopens a
handle, which are two operations sharing a word rather than two spellings of one.

**The mode words do not fold**, so the bad-mode message is M5's *reporter* and
not M5's *suggester* — S1201, which lists all four. A "did you mean" over four
candidates is a guess where an enumeration is available. What that decision
rests on is §2.4.

**The eleven rows with no call shape now have six**, written out of v1's
recorded arities: `open(path, mode)`, `clear(path)`, `change(d)`, `current()`,
`exists(d)`, `delete(x)`. **`words.def` carries the same shapes and had no
choice**: `words_walk.hpp`'s `match_shape` compares a row's argument list to the
written one character for character, so a §2.2 saying `open(path, mode)` over a
registry saying `open` is a path `words_test` cannot walk. Measured before the
change — `satellite.file.open("x", "read")` already resolved to `1 8 2` through
the bare-word arm, and so did `satellite.file.open("x")`, which would have
refused one layer later. The shapes are what make the arity a resolve-time fact,
which is §1.3's whole claim.

### 2.2 A file is the first thing in this language that two names can share

**Every other handle in `Value` is `shared_ptr<const T>`.** A string, a float, a
list and a map are all bodies nothing can mutate: every change is a copy
published whole through the receiver's storage slot (DESIGN §6.4), so a value
two slots see can never move under either of them. **A file is the deliberate
opposite**, and DESIGN §8's table has said so since before any of this was
built — *"handle | reference type"*.

So the arm is `shared_ptr<FileHandle>` with **no `const`**, and it is the sixth
append to the variant. Writing it as `shared_ptr<const FileHandle>` with mutable
atomics inside would have been the same semantics with a `const` that lied about
them. Sixteen bytes against the 32-byte widest arm, so §8.2's forty-byte assert
did not move — `Str`'s accounting for the fifth time.

***AND EQUALITY HAD TO BE TOLD, WHICH IS THE PART THAT WOULD HAVE BEEN SILENT.***
`same()` ends with a fall-through whose comment reads *"BOTH ARE Nothing OR BOTH
ARE Runtime, and in either case they are equal because neither arm holds
anything to differ about"* — and the index check above it has already proved
both sides are the same arm. **A file arm added without touching that function
makes every two files equal.** Two separate opens on one name are two
descriptions with two cursors: reading a line from one does not advance the
other, closing one leaves the other open. The arm answers **identity**, which is
the only answer a reference type has, and `tests/file_test/round_trip.cpp`'s last
fixture is that sentence written as a test — `a == b` false for two opens, true
for an assignment, and `b.ok()` still true after `a.close()`.

**The `std::atomic` fd comes across from v1 with its reason**, and PLAN's line
about it holds: **M23 is when that first gets exercised, not when it gets
written.** What is new and is named rather than discovered is that **the read
cursor is not atomic** — `read_at`, `buffer` and `buffer_at` are one logical
position spread over three fields, and making each atomic would make each field
consistent and the position no more so. Two threads reading one handle is a
design question about what a shared handle MEANS, which is the same question
DESIGN §8 leaves open for the socket.

### 2.3 The cursor is forced, and by a sentence written seven milestones earlier

**v1 has no read cursor and its reason is sound.** `.read()` seeks to 0 on every
call, because with no `.seek()` in the language *read from wherever the offset
happens to be* is a question no satellite program can pose. PLAN carried that
forward as an open item: *"Does `read_line` advance a per-handle cursor?"*

**DESIGN §8.7 had already answered it, at M12, and names M19 as the inheritor.**
*"`satellite.console.typed()` and `satellite.variable.file.read_line` answer a
line, or nothing, assignable anywhere."* **That sentence has no meaning on a
handle that rewinds every call.** So the cursor is not a decision this milestone
took; it is one it discovered had been taken, and the open item was open only
because nobody had read the two documents together.

***EVERY READ IS A `pread` AND THAT IS THE WHOLE OF THE DESIGN.*** `"read_append"`
is `O_RDWR | O_APPEND` — forced, because POSIX gives one file offset per open
file description and there is no `.seek()`, so a bare `O_RDWR` write would land
wherever the last read left the shared offset. **But `O_APPEND` moves that
shared offset to the end of the file on every write.** A read cursor riding on it
would be silently reset by every `write_line`, in the one mode whose entire
purpose is writing and reading back through one handle. `pread` takes its
position as an argument and moves nothing, so the read side stops using the
shared offset at all. `tests/file_test/reading.cpp` fixture 5 — a write between
two reads — is the fixture a `read`-based implementation fails.

**`read_all` reads from the beginning and leaves the cursor at the end**, so a
`read_line` after one answers nothing. The two verbs share one position and this
says which way it moves: leaving it where it was would make `read_all` mean
*"the whole file"* and *"and nothing happened"*, which is not true of a handle.

**And the buffer is not an optimisation.** Without it `read_line` either issues
one syscall per byte or re-reads its chunk's tail on every call, and the second
is quadratic in the file — which is not a thing to give a language its only line
reader. It is 65536 bytes and **that is not a limit on anything**: fixture 6
writes a 70000-character line and reads it back whole, because NO_LIMITS §1 is
the rule a chunk size must not quietly become.

### 2.4 The fold was guessing, and it had been wrong in shipped code for three milestones

***`f.write("one")` REFUSED ON ITS FIRST RUN,*** with

    error S0524: `one` is not an option write has -- it has line

**WORD_NUMBERS §1.5's literal-option fold decides which words take options by
reading spellings**: a word takes options when a sibling is spelled
`<word>_<something>`, so `sort` takes options because `sort_down` sits beside it.
`write(x)` `1 6 2 11` had just been minted beside `write_line(s)` `1 6 2 4`.

**Measured over the whole registry, that rule fires on three words and is right
about one:**

| word | what the fold believed its options were | true? |
|---|---|---|
| `sort` | `down`, `up` | yes |
| `remove` | `at`, `first`, `last` | **no** — three separate verbs |
| `write` | `line` | **no** — two separate verbs |

***SO `parts.remove("bolt")` — TAKING A STRING OUT OF A LIST OF STRINGS — COULD
NOT BE WRITTEN, AND HAD NOT BEEN WRITEABLE SINCE M16.*** It refused with the
same S0524. **And M18's help pass wrote the defect down as the language**: it is
the fourth of the five *"plainly stated and plainly wrong"* corrections in
`help_lines/README.md` — *"a quoted word inside `list.remove` is read as an
option name rather than as a value"* — and `1 4 2 19`'s worked example was
rewritten to hold the value in a variable first, so that it ran. **`verify.py`
passed it.** A worked line proves the sentence beside it runs; it cannot prove
the sentence is the one that should have been written, and that is the failure
mode this milestone found in the thing built to prevent failures of that kind.

**The author's fix, asked for in those words: make a table of the words that
take options and have the compiler look at it.** `words.def` gains a sixth small
list beside `SAT_PLACE`, `SAT_BUILT` and `SAT_TOPIC` — **one row, `sort`** — and
`fold_option` reads it. Renaming `write` was available and was declined: **two
words in two milestones is a rule that is wrong, not two unlucky names.**

**IT IS ALSO CHEAPER THAN THE GUESS, which is worth stating because a lookup
table sounds like a cost.** The guess walked EVERY CHILD of the receiver's type
on every selector call with a string literal in front — twenty-six of them for a
list, with a string prefix compare each. `takes_options` is one integer compare
against the parent, which fails for every receiver that is not a list and never
reaches a character, and it returns the moment it knows.

**PLAN's M7 entry said the mode words would fold "with no edit" and that was
false on two counts**, both measured here: `fold_option` has one caller, the
SELECTOR arm, so a whole-path module call never reaches it; and it inspects
argument 0, while `open`'s mode word is argument 1. The bullet is corrected where
it stands. The author then settled the question the other way anyway — the mode
words do not fold — so what M19 owes the fold is the correction and not a use.

### 2.5 `+` joins two strings, because the diagnostics could not be written

`display("the reason: " + f.error())` was S0711, *"`+` works on two numbers"*.
**`append(x)` `1 6 1 14` MUTATES its receiver** under §6.4's storage-slot rule,
so every string built out of pieces needed a variable to be built in — and a
string used once and named nowhere is exactly the shape of every file
diagnostic this milestone writes. Two example programs already in the tree,
`advanced.satl` and `class_test.satl`, had been written with `+` on strings and
could not run.

**It is one operator over two types and not a second meaning for the
character.** Addition and joining are the same shape: two of a thing in, one of
that thing out, neither changed. **Nothing is converted** — `"n = " + 4` is
still refused, so this is not the truthiness ladder DESIGN §1.1 exists to keep
out, and a program that wants that writes `4.to_string()` out loud. DESIGN §6.6
carries it.

### 2.6 Two states a descriptor of -1 was collapsing

**A help example found it.** A leftover file from an earlier run made
`satellite.file.new` come back `EEXIST`, and the next line of the program said

    error S1203: `write_line` was asked of a `satellite.variable.file` that is
                 closed

**about a handle that had never been open**, three lines under the call that
failed to open it, while the `errno` explaining the whole thing sat unread in
`error`. A message that points away from the answer is worse than a shorter one.
**S1208 is the second sentence**, and the two are told apart by
`FileHandle::ever_open` rather than by whether an errno is held — a handle that
opened, failed one write and was then closed holds an errno and HAS been open,
so the obvious derivation is the wrong one.

## 3. The test, and the two things a running program cannot check about itself

`example/persistence.satl` is one of the two done-when programs and it prints
one `PASS`. **It cannot be the whole check, for two reasons.**

**A refusal ends the program.** Seven of the eight S12xx codes are reachable
only by a program that stops, so a fixture for each needs its own program, and
`tests/file_test/refusals.cpp` is eight of them. **The CODE is asserted and not
the text** — M18's argument, which its own done-when learned the hard way: a
suite checking only that *something* refused would pass if all eight raised
S0713.

**And a refusal and a false answer look the same from the outside.**
`persistence.satl` asserts `f.ok()` is false for a missing file and prints
`PASS` — and it would print `PASS` just as readily if the language refused
instead, because the refusal ends the program before the `PASS` and a missing
`PASS` is also what a broken suite looks like. Every fixture in `file_test`
asserts **whether anything refused** as well as what was answered.

**The suite makes its own directory with `mkdtemp` and removes it.** The subject
is a filesystem and `satellite.file.new` is O_EXCL, so a suite that wrote into
the tree would pass once and fail on every run after — the exact defect PLAN M19
forbids in the acceptance program, arriving in the thing that checks it.

**Its last fixture asserts what was left behind, and the answer is not
nothing:** eight files, exactly the ones whose programs refused before reaching
their own cleanup line. That is a true fact about how a refusal behaves,
asserted rather than worked around — and it is where the module's claim to sort
as `SatString`s and not as bytes is actually exercised, because `closed2.txt`
sorts **before** `closed.txt`: a digit beats punctuation in DESIGN §5's table.
Written in ASCII order first, and it failed.

**Every one of the 167 runnable worked lines in `HELP.md` passes**, twenty-eight
of them new here.

**And one thing this suite could not have caught, which cost a wrong belief for
about a minute.** `make file_test` failed on a `static_assert` — errors.def's
numbers must ascend and S1208 had been inserted before S1207 — and the previous
binary was still sitting in `tests/file_test/`. Running it by hand printed
`file_test: ok`, from objects compiled before the change under test. **That
green line is indistinguishable from the real one**, and no edit to the Makefile
can prevent it, because it is a person running a binary rather than make
building one. `make_support/065-tests.mk` names it as the third member of a
family whose other two members it already documents, and FORMAT/CXX.md §6.4 is
the rule: `make <name>_test && ls -la <the binary>`, where the `&&` is the whole
of it.

## 4. What it left open

- **`satellite.directory` still has no create verb, and `1 18 6` is free.** The
  done-when needs none and a verb minted to round out a namespace is a verb
  designed by symmetry. Named here so that the next milestone to want one finds
  a hole rather than a surprise.
- **The caret on S1201 sits under the call and not under the bad word.** A
  handler is handed values and not argument spans, so `m.span_of(m.here())` is
  the whole call. Every module in the tree has this and none of them has needed
  it enough yet; the sentence names all four modes, which is what the done-when
  asks for.
- **A method on a call result is still S0720.** `f.read_all().size()` does not
  compile — names.cpp folds a selector only through a DECLARED name — so three
  help examples and five test fixtures bind to a variable first. That is not
  M19's boundary, but this milestone is the first to write enough chained calls
  to keep hitting it, so **it is now written down where it is caused rather than
  where it was felt**: WORD_NUMBERS §1.5 states it as a consequence of the one
  hop, `help_lines/README.md` states it for anyone writing an example, and
  PLAN §8's M19.5 and M19.6 entries each carry it as a working note. **No
  milestone owns loosening it** — `compile_expressions.cpp` says the case
  "waits for the type rules that would see through it" and §8 promises none.
- **Two threads on one handle.** The fd is atomic and the cursor is not. M23.
- **`satellite.variable.binary` and `.hex` are M19.5**, minted as a milestone
  here because `write(x)` is the verb they will be written with and DESIGN §8.5
  had specified them since before M9 with no milestone owning them.
- **The `.satc` written after resolve, and the option token, are M19.6** — the
  author's idea, `0#down` rather than `0#"down"`. What blocks it is not
  SATC §3's rule about literals but the ORDER: the writer takes the parse tree,
  and whether a literal is an option depends on the receiver's declared type,
  which is resolve's answer.
