# M19.6 — the `.satc` written after resolve, and the option token

**Landed 2026-09-09** (`05c1757`).

**NO NEW PATHS.** PLAN's entry says so and it stayed true: not one row was added
to `words.def`, and the numbering is byte-identical to M19.5's. What moved is
**when** the `.satc` is written, and what that made writable.

**THE MILESTONE WAS NOT "ADD A TOKEN".** The author's idea was one sentence —
*"`#` stands for a number in a `.satc` file, so `0#` stands for an option"* — and
the token is four lines of writer and thirty of reader. What cost the milestone
was that `cache_command.cpp` handed the writer `out.parsed.ast` and nothing from
resolve, so whether `"down"` was an option could not be known where the decision
had to be written. PLAN said this before the work started and it was right:
**the milestone is the move, and the token is what the move made writable.**

## 1. What is built

| | before | after |
|---|---|---|
| when the `.satc` is written | after the parse | **after resolve** |
| what a fold looks like in the file | `my_list.sort("down")` | **`my_list.sort(0#down)`** |
| what a warm run does with it | decides again, every run | **looks the row up, once** |
| a program that parses and does not resolve | is cached | **is not** |
| `errors.def` rows | 113 | **114** — S0307 |

**Three new things and one removed.** `cache::Folded` is the reader's answer —
which selectors the file said were folded, as bare offsets. `cache::Folds` is
the writer's question, filled by `resolve::folds_of()`. **S0307** refuses an
option token that names no call. And `Reading::resolved` is what made
`resolve_command.cpp` stop resolving a second time.

**`0#down` NAMES THE OPTION AND NOT THE ROW, WHICH THE AUTHOR CHOSE AND WHICH
COSTS SOMETHING.** `#1.4.2.5` would have said the answer outright and made a
warm read free; `0#down` says which word the program wrote, so the file still
reads as the program it came from. §3 is what that costs.

## 2. What was decided, and by whom

| | decided | by |
|---|---|---|
| the spelling | `0#down` | the author, 2026-09-08 |
| quotes on the option | **none** — `0#"down"` says it twice | the author, 2026-09-08 |
| names the option or the row | **the option** | the author, 2026-09-09 |
| do method names get numbers too | **no, they stay words** | the author, 2026-09-09 |
| does `satl <file>` use the cache | **not this milestone** | the author, 2026-09-09 |

**THE LAST TWO ARE REFUSALS AND THEY ARE WHY THIS MILESTONE IS SMALL.** Both
were offered with a measurement attached and both were declined, which is the
shape M19.5's split already paid for.

**Numbering a selector** would have removed about twenty of the thirty-two walks
a warm run still does on `example/containers.satl` — but M4.5 measured the
`fsync` dominating a cold run, and §3's table below shows the warm case already
within 0.05 ms of the floor. It also has a real problem under it: a language
selector's number is a property of the BUILD and a user's is a property of the
RUN, and the file has no way to say which one it is holding. `words_runtime.hpp`
has warned about exactly that since M2.

**Wiring the cache into `satl <file>`** is a larger thing that this milestone
found rather than did — §5.

## 3. What it costs, measured

**PLAN asked for this rather than for an assertion**, because §5's promise is
that the first run is never slower for having produced a `.satc` and the write
thread now starts one pass later. Same machine, same build flags, min of 50, and
the baseline is `89dc0c4` — the commit immediately before the move:

| | before the move | after |
|---|---|---|
| `satl --version` (the floor) | 2.01 ms | 1.99 ms |
| `satl --satc hello_world.satl`, cold | 3.77 ms | 3.75 ms |
| `satl --resolve frames.satl`, cold | 3.90 ms | 3.90 ms |

**It is free, and one measurement had to be thrown away to say so.** The first
attempt compared `satl` against `satl.haswell` — yesterday's binary, sitting in
the tree, and the obvious thing to reach for — and reported a **0.17 ms
regression that does not exist**. Those two are built with different `-march`,
so what it measured was codegen. **The wrong number was believable**, which is
the reason it is written here: it agreed with the intuition that adding a pass
costs something, and the right number does not.

**AND ONE REAL COST WAS FOUND BY THE SAME MEASUREMENT AND FIXED.**
`resolve_command.cpp` opened as `resolve::Resolved resolved = read.resolved;`,
which copies one `Info` per AST node. It is a `std::move` now. Found because
`--resolve` is the arm that does exactly the same work it did before this
milestone, so anything it lost was mine.

**M4.5's table, re-taken** — the numbers are ~0.3 ms above the ones it recorded
on 2026-08-30, and **the floor moved with them**, which is what says it is eight
milestones of binary and not this one:

| | M4.5, 2026-08-30 | M19.6, 2026-09-09 |
|---|---|---|
| `satl --version` | 1.61 ms | 1.91 ms |
| `--satc hello_world.satl`, warm | 1.74 ms | 1.96 ms |
| `--satc containers.satl`, warm | — | 2.47 ms |

**WHAT A WARM RUN SAVES IS COUNTED AND NOT TIMED**, which is the rule
MILESTONES/M7.md set and the only thing that can catch the skip disappearing.
`example/containers.satl`, which writes all three fold shapes on three lines:

| | walked | from the `.satc` |
|---|---|---|
| before M19.6 | 32 | 40 |
| after | **30** | **42** |

**Two, and there are exactly two folded calls in the file.** The third `sort()`
has no option and is still walked for, which is the selector question the author
declined.

## 4. What building it found

### 4.1 The closing quote, and nine days of a cache that never read

**Found before the milestone started, by trying to measure a cold run.**
`unnumber()` copied a string's opening quote and its contents and then handed
the **closing** quote back to the top of the loop, which read it as an opening
one. Everything after a string on that line was copied through as string
contents — a `#` in it reached the parser as itself — and the contents of the
next string were read as code.

    #1.6.6 b = #1.8.5("no_such") == #1.17.1

**A string and a path on ONE line is what it takes.** The inner loop also stops
at a newline — a literal may not cross one — so every line began in the right
state and only a line with both went wrong. `example/persistence.satl` was the
only acceptance program with that shape, and it entered the tree at M19 on
2026-09-08 — **nine days** after `section_reading()`'s four fixtures were chosen
at M4.5, and **one day** before this found it.
`literals_are_not_scanned()` wrote its string **last** on the line, which is the
one position that hides this.

***THE FIRST VERSION OF THIS SECTION SAID "five months" AND SO DID `89dc0c4`'s
COMMIT MESSAGE.*** It is nine days: M4.5 landed 2026-08-30, M19 landed
2026-09-08, and this was found on 2026-09-09. **The wrong number made the
finding sound better than it was** — a defect that survives five months of
testing is a statement about the tests, and one that survives nine days in which
the exposing shape existed for one of them is a statement about nothing much.
Corrected here rather than by rewriting the commit, which is the same choice
this directory's convention makes about a hash.

**SATC §4 IS WHY IT WAS SILENT AND WHY IT WAS SAFE.** *"A missing, stale or
unreadable `.satc` is never an error"* held under a genuinely broken reader: the
program ran from its source and was right the whole time. What it cost was the
cache — such a program wrote a file on every run and read one on none of them.
**That is the design working**, and it is the strongest thing this milestone can
say about whether the format is a good idea.

Landed separately in `89dc0c4`, before the milestone, so that M19.6's token was
not built on top of it.

### 4.2 The Mark has to go on the selector, and the reader is behind it

`numbers.cpp` looks a Mark up by `ast_.token_of(anchored).end` with `anchored =
ast_[call].a` — the **Member** node, anchored at the word `sort`. A Mark sitting
where `0#down` ends would key on the String node and no selector would ever find
it. So `unnumber()` walks **back** over the word: `selector_ends_before()` is a
lookbehind, and it is safe only because the writer emits `name(` with nothing
between them.

### 4.3 `0#up` needs two lookups, and the first version only did one

`example/containers.satl` writes `sort()`, `sort("down")` and `sort("up")` on
three lines, and they take three different routes. **`sort_up` is not a row** —
§2.2 assigns `sort()` as "ascending, no key" and that IS sorting up — so M16's
rule lets the fold land on the bare word. The cached branch tried the folded
spelling only, missed, and fell through to decide the whole thing again. It was
**correct and silently paying** for what the milestone removed.

**The test that caught it had to be rewritten to be able to.**
`origin_of(run, "1 4 2 3")` answers about the **first** node with that number,
and this fixture has two: the bare `sort()`, walked, and the folded `sort("up")`,
cached. `count_origin()` is the replacement, and the assertion is now stronger
than the one that failed — one walked *and* one cached, which says the token did
the work rather than the number.

### 4.4 The dependency only points one way

`name_resolver/resolve.hpp` includes `satellite_cache/cache.hpp`, because
`resolve()` takes `cache::Marks`. So the writer **cannot** name
`resolve::Resolved` — it would close the cycle. `cache::Folds` is a
`std::vector<bool>` the caller fills, which is the seam `eval::Policy::interrupted`
already keeps. `folds_of()` lives in `name_resolver`, the side that may name
both.

## 5. What is left open

1. **`satl <file>` still never reads or writes a `.satc`.** Only `--satc` and
   `--resolve` call `read_program()`; the run, the check arms and the prompt go
   through `build_program()`, which opens the source and parses. **SATC.md §1's
   "on the next run satl reads it instead of doing the walk again" describes
   the RUN and the run does not do it.** Found while measuring this milestone,
   recorded rather than fixed at the author's direction. The hard part is not
   the cache — the header line, the stat and the storage are all built and
   working — it is that a warm run which finds a problem draws its caret into
   the `.satc`; `resolve_command.cpp` solves that by throwing the run away and
   re-reading, and every run would inherit it.
2. **A selector still has no number in the file**, and §2 says why it was
   declined rather than forgotten. The two halves of §3.1's rule genuinely have
   different answers and nothing yet says which is which.
3. **`satellite.include` of a spaceship is still SATC §6's open bullet**, and
   M19.6 makes it sharper rather than closing it. A `.satc` now records a
   decision about the program's TYPES, and a type declared in an included file
   could change without the including file's mtime moving. **It does not bite
   today** — `satellite.include(satellite)` is the only include there is, and
   including another file is M25 — so the `source` line answers it for now.
4. **Nothing prunes the cache directory**, unchanged from M4.5 §6 item 3.

## 6. What proves it

| | |
|---|---|
| the round trip, cold and warm | `tests/resolve_test/cache.cpp` — `section_option_token()`, all three fold shapes |
| the reader alone | `tests/satc_test/reading.cpp` — `the_option_token()` |
| the refusal | S0307, and `codes.cpp`'s row count moved 113 → 114 |
| the whole tree | 14 suites, all green |
| the examples | all 19 round-trip; `containers.satl` carries `0#down` and `0#up` |

**THE MUTATIONS THAT FAIL IT.** Removing the two lines that consume the closing
quote fails `the_option_token()` and `literals_are_not_scanned()`. Dropping the
bare-word retry in the cached branch fails §4.3's `count_origin` assertion and
nothing else. Writing the Mark at the option's end rather than the selector's
fails every `Origin::Cached` check in `section_option_token()`. Passing `false`
for `first_is_an_option` in `write_expressions.cpp` writes `"down"` and the file
still round-trips — caught by the `satc.find("0#down")` assertion, which is why
the test looks at the TEXT and not only at the numbers.
