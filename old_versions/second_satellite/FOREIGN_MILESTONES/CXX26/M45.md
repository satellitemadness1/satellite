# CXX26/M45 — a declared string encoding

**C++26 feature:** `std::text_encoding` (P1885).

**Answer: satellite milestone M45 — and it is a question satellite has not
asked itself yet.**

## What C++ is doing

Naming the encoding a program's text is in, so a library can convert rather than
guess, and so "the locale decides" stops being the answer.

## What satellite has

`satellite.variable.string`, and **no stated encoding at all**.

`satellite_string/satellite_string.cpp` stores bytes. `size()` answers bytes,
not characters. `at(n)` answers a byte. `upper()` and `lower()` work on the
bytes they understand. So:

- a string holding UTF-8 reports a size larger than its character count
- `at(n)` inside a multi-byte character answers half a character
- `upper()` on anything outside ASCII does nothing, quietly

None of that is written down anywhere, which is the actual problem: **the
behaviour is defensible and undocumented.** A reader cannot find out what a
string is without reading the C++.

## What M45 should bring, in order

1. **Say what a string is today.** One paragraph in DESIGN: bytes, and the
   methods that count them count bytes. This costs nothing and removes the
   ambiguity — it is worth doing even if nothing else here ever ships.
2. **Decide whether `size()` is a promise.** If a program is ever to hold text
   rather than bytes, `size()` answering bytes is the decision that will be
   hardest to change later, because every program written before the change
   depends on it.
3. **Only then** consider a declared encoding and conversion.

## What it must not break

Step 1 breaks nothing and should not wait for the rest. **Step 2 is a language
change and gets harder every week** — this is the milestone most likely to be
cheap now and expensive later, which is the reason to write it down before
anybody needs it.
