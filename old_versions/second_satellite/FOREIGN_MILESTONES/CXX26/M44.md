# CXX26/M44 — a file's bytes at parse time

**C++26 feature:** `#embed` (adopted from C23).

**Answer: satellite milestone M44.**

## What C++ is doing

```cpp
static const unsigned char icon[] = {
#embed "icon.png"
};
```

The file's bytes become a literal at compile time — no build step, no
xxd-generated header, no runtime open.

## What satellite makes you write instead

`satellite.file.open(path, "read")` and `read_all()`, at run time, every run.
Which means the data is not part of the program: ship the `.satl` without the
file beside it and the program refuses where it used to work.

There is no other route. `satellite.library.<name> = <literal>` takes a literal
a person typed, and there is no way to make one from a file.

## What it would cost to build

Less than most of this folder, because the machinery is adjacent:

- a path — `satellite.include.bytes("file")` or similar — resolved at parse time
- the resolver reading the file, exactly as `satellite.include` already reads one
- the bytes landing as a `satellite.variable.bits` or a string literal
- the `.satc` cache carrying them, which is the part with a size question:
  a 10 MB embed makes a 10 MB cache entry, and `satellite_cache/` has opinions
  about what belongs in one

## What it must not break

Reproducibility of the cache. `.satc` is keyed on the source; an embed makes the
program depend on a second file, so the cache key has to cover it or a changed
asset silently reuses the old bytes. That is the whole of the work's risk and it
is a solved problem — the key includes the embedded file's identity too.
