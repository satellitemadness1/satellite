# M9 — the value model and closure compilation

**Landed 2026-09-01** (`PENDING`).

[PLAN.md](../PLAN.md) §2.3 and §2.4 are the specification, §2.5 and §2.6 are the
constraint that decides its shape, [DESIGN.md](../DESIGN.md) §7.5 is the rule and
§8 is the value model, and
[SCRATCH.md/NO_LIMITS.md](../SCRATCH.md/NO_LIMITS.md) §5.5 is what this milestone
was told it had to be. This is a **review and not a plan** — what was decided on
the way, what building it found, what it left open, and which measurements prove
its test.

**Two new modules, twenty-two files of `src/`, eight of `tests/`.**
`satellite_value/` is `Value` and the six live codes M3 stubbed; `evaluator/` is
the closure compiler, the machine that walks it, `handlers[path_id]` and the
inline caches. `satl` gained `--compile` and `--call`, and **satellite ran its
first program**: `satl --call example/frames.satl factorial 10` answers 3628800.

---

## 1. What the milestone was

**Three things, and the third is what the other two are for.**

1. **`Value`** — DESIGN §8's table, at DESIGN §8.2's forty bytes, with the small
   case never allocating. And `Str`, which is PLAN §6.1's port finished: the six
   live codes of DESIGN §5's table, answered from the machine.
2. **Closure compilation** — PLAN §2.3. The arena AST compiles to a tree of
   24-byte PODs, module calls dispatch through `handlers[path_id]`, and a call
   site caches what it resolved to (§2.4). That is the third of the three
   adoptions §2.6 orders and the milestone that owns them.
3. **AN EXPLICIT CONTROL STACK, WHICH IS THE ONE THING ABOUT THIS MILESTONE THAT
   CHANGED.** PLAN §8's M9 entry used to say *"recursion depth is bounded here"*.
   The author reversed that on 2026-08-31 — *"if the recursion shuts the program
   off after 20,000 then that is not a working interpreter, that's a broken
   interpreter"* — and DESIGN §7.5 was rewritten to match. So a satellite
   program's recursion is bounded by memory and by nothing else.

**M8.5 is why this milestone did not have to do it twice.** PLAN §2.6 put the
four static passes ahead of it: *"closure compilation then emits onto a stack
that already exists rather than growing one afterwards. Doing them in the other
order means doing the evaluator twice."* That held. What it did not predict is
that a FIFTH walk would be needed — see §4.1.

## 3. What was decided on the way

### 3.1 An op is five words, which is the shape a Node already had

`ast.hpp` makes a `Node` a kind and four payload words in 24 bytes. An `Op` is a
**function pointer** and the same four payload words, in the same 24. That
symmetry is not decoration: closure compilation is §2.3's *"every decision that
CAN be made before execution IS"*, and what it replaces is precisely the kind
byte — a tag the evaluator would have tested at every node becomes the address it
would have jumped to. §2.3's *"at runtime a node is one indirect call with no tag
test and no re-resolution"* is that sentence, and `static_assert(sizeof(Op) ==
24)` is where it is kept.

**The source node is a side table and not a field**, which is PLAN §2.2's
decision about `Name::slot` applied one layer on. A span is wanted when a
diagnostic is raised and when `--compile` prints; on neither path does one more
indirection matter, and on the walk it would be four bytes of every cache line
spent on something the walk never reads.

### 3.2 A call owns its frame from both ends, and there is no sentinel op

The obvious design pushes an *end of frame* marker under a capsule's body so that
falling off the end has something to pop the frame. This does not, because **the
call op is already sitting on the work stack underneath** and can be resumed: its
step 2 is the implicit `satellite.return()`. A real return truncates the work
stack to below that op, so the two paths leave identical state and `unwind()` is
the one place a frame is popped.

**`Machine::call()` needed the same road**, and that is what `Capsule::entry`
is. A call from C++ has no call op to be resumed and `Frame::work_floor` is an
index into that stack — so without an `op_enter` there would have been a second
way to build a frame. DESIGN §7.1 is the receipt for what a second way to get a
frame wrong costs: one registry, and a recursive `fact` that answered 1 for every
input.

### 3.3 The compiler is the machine with the nouns changed

`tasks_` is `work_`, `results_` is `value_`, and `again()`/`visit()`/`finish()`
are `again()`/`push()`/`done()`. A compiler and an evaluator are the same walk
over the same tree: one leaves op indices behind and the other leaves values.

**Nothing was factored out of the two**, because they share no type — the
resemblance is the point and a shared base class would hide it. What IS shared is
MILESTONES/M8.5.md §3.3's rule about which direction a case reads: a stack pops
backwards, so `visit_reversed()` and `take_many()` are the two places the
inversion lives and every case above them reads forwards.

### 3.4 The policy is handed in, and that is what makes the depth fixtures worth anything

`Machine` takes a `Policy` — the control-stack ceiling and `division_digits` —
rather than reading `machine_limits`. `satl` fills it from the dials;
`tests/eval_test` fills it itself, **and so links no `machine_limits` at all**.

**That is M8.5 §4.1's finding used rather than repeated.** A 20,000-deep resolve
fixture spent a day passing against a raised `RLIMIT_STACK` it had never been
given, because the test binary did not link the module that raises one. Here the
omission is deliberate and written into `065-tests.mk`: every fixture in
`tests/eval_test/depth.cpp` runs against the 8 MiB a login shell hands out, so a
1,000,000-frame recursion means what it says.

### 3.5 Unset `max_depth` means `MEMORY_MAX`, which is the machine

PLAN §8's M9 entry says the default is *"the machine"*, citing §4.5.4's answer
for `MEMORY_MAX` — *"a fraction is a number satl would have invented about a
program it has never seen"*. That could have been read as `mem_total_bytes()`.
It reads the sibling dial instead, and the two are **the same number whenever
nobody has set either**.

**Where they differ, reading the sibling is the answer that works.** A user who
sets `MEMORY_MAX=1GiB` has said satl may have a gigabyte; a control-stack ceiling
above that could never be reached, because M6's watchdog would stop the run
first — with the sentence this dial exists to improve on. Measured: under
`MEMORY_MAX=2GiB` with no `max_depth`, a runaway recursion is refused at 1.7 GiB
with S0701 rather than by the watchdog with its memory sentence. NO_LIMITS §8
question 1 carries the table.

### 3.6 A ceiling reached is EXIT_LIMIT and not EXIT_MALFORMED

`programs/opening.hpp` gives `EXIT_MALFORMED` the meaning *"a file satl was given
is not what it has to be"* and `EXIT_LIMIT` the meaning *"satl stopped itself: a
machine limit was reached"*. A program that filled the control stack **may be
perfectly correct** and simply asked for more than it was allowed, so `Ending`
has three values rather than two and S0701 exits 4. M6 built that status for the
watchdog and this is its second producer, which is the shape NO_LIMITS §7 asks
for: the same event caught one layer in, with a better sentence and the same
number for a script to read.

### 3.7 The dispatch table is process-wide, and that is safe for a reason worth writing down

`words_runtime.hpp` warns in capitals that *"a user's PathId is valid inside one
run only"*, and M22 runs many programs in one process. That warning is about
paths a PROGRAM interned, and **nothing may be keyed on one here**: every handler
is installed for a path `words.def` numbers, which is constexpr data identical in
every run of every process. The table is a property of the build rather than of a
run.

It is also **empty in `satl` at M9**, which is the milestone boundary rather than
a gap: PLAN §8's path ledger gives M9 none of the 223 numbered paths, because
*"M5 and M9 build the machinery every other row dispatches through"*.
`tests/eval_test/dispatch.cpp` installs its own and is the consumer PLAN M2's
rule asks for.

### 3.8 The cache cell is allocated at compile time, not on first execution

PLAN §2.4 says a `Call` node *"caches the resolved PathId and handler pointer on
first execution, behind a guard"*. The **cell** is allocated when the op is
emitted and lives in a side table indexed by call site. That keeps the op arena
immutable and shareable, which is what DESIGN §10.5's threads need: one arena,
one cache vector per run.

## 4. What building it found

### 4.1 The compiler is a fifth walk, and it had to be born iterative

M8.5 rewrote four walkers to keep their own stacks. **The closure compiler is a
fifth and it did not exist then.** DESIGN §7.5 has no exception for a pass that
runs once: a program that parses at 100,000 deep and then segfaults being
COMPILED would have moved M8.5's crash rather than removed it. So it was written
in the shape the other four were rewritten into, and
`tests/eval_test/compiling.cpp` checks a 100,000-deep expression compiles at
8 MiB.

**Worth saying because it is the general form.** Every future pass over the arena
inherits this — M16's search walk, M18's help, whatever reads a tree at M27 — and
the rule is not "rewrite the walkers", it is *no walk over user-controlled depth
uses the C++ stack*, from its first commit.

### 4.2 Every program in `example/` opened with something M9 refused

The first version compiled `satellite.include` to a refusal naming M25, on the
reasoning that spaceships are M25's. **Every acceptance program in `example/`
begins `satellite.include(satellite)`**, so `satl --call example/frames.satl
factorial 10` stopped on line 5 with a sentence about M25.

DESIGN §3 had already settled it, three documents over: *"`satellite.include(
satellite)` is the one include form that does nothing, and that is not a
leftover — it means 'include the runtime', which a running program already has.
Every other form names a spaceship and loads it."* So it compiles to no op, and
only the spaceship form refuses.

**The finding is which check caught it.** `tests/eval_test` was written and
green; the acceptance files were what failed, because a fixture opens with the
capsule it is about and a real program opens with its preamble. LAYOUT.md calls
the files in `example/` *"not samples — each of these is what a milestone means
by done"*, and this is the first time that has been load-bearing rather than
true.

### 4.3 A global could be declared and never read

`satellite.library.total = 42` numbers `total` under `satellite.library` at parse
time — `parser_declarations.cpp` hands `NodeId::LIBRARY` in as the owner. Reading
it back was **S0521, "`total` is not a word the language has under
satellite.library"**: true of the language and false of the program.
`cache::language_path` walks the FROZEN table, so the walk stopped at `total` and
the resolver refused it.

**Nothing could see it until something could hold a value.** M7 numbered the
declaration and `satl --resolve` printed the number; a global that can be
declared and not read is indistinguishable from a working one until there is an
evaluator. The fix is six lines in `name_resolver/names.cpp` — when the walk
stops at a segment that IS this node's own name, ask the run's numbering — and
it is narrow on purpose: `satellite.library.total.foo` still stops at `total` and
is still refused, because the outer node is not where the walk gave up.

**The `.satc` writer needed no change and that was checked rather than assumed.**
It calls `language_path` itself rather than reading resolve's answer, so a user's
PathId never reaches it and SATC.md §3's rule that only language words become
numbers is untouched.

### 4.4 The dial meant bytes and its syntax had not been told

`max_depth=64MiB` was answered with **"max_depth is a whole number and `64MiB` is
not one"**. Every dial was `Kind::Dial` — a bare integer — which was right while
no dial meant a quantity of memory. The 2026-09-01 reading makes this one a
memory ceiling, which puts it beside `MEMORY_MAX` rather than beside a count of
digits, and PLAN §4.5.4's argument for units is the same here as there: 61.9 GiB
and 64.9 GB are the same memory, so a bare number is an ambiguity.

So dials have a `kDialKinds` table now. **And it forced a second thing apart that
had been one test**: `config.cpp` used `kind != Kind::Dial` to mean *"this is a
machine setting, so `arguments.memory.total` is a legal value"*. Those are two
different claims and they came apart the moment a dial took a size — DESIGN §7.7
pairs three settings with three paths, and a fourth pairing is not something a
kind gets to invent.

### 4.5 The range PLAN asked for does not exist

PLAN §8's M9 entry says **"THE RANGE AND THE READER LAND TOGETHER, AT M9"**,
citing M8 §6.1 on what a dial with a bound and a silent policy costs. The reader
landed. There is no range, and the reason was already written two rows away in
`config_internal.hpp` about `min_free_mb`: *"a meaning with no bound ever claimed
for it"*.

**Any number of bytes is a number of bytes.** Zero refuses the first push and
says so with a caret; a number wider than any machine means the machine. Neither
is a value satl cannot act on, and that is the only thing S0807 and S0808 are
for. So the row still reads `{false, 0, 0}` and **the reason under it changed** —
from `float_digits`'s reason, which is "no consumer yet", to `min_free_mb`'s.

### 4.6 `human_bytes` got a second consumer and moved

S0701 says how many bytes a runaway recursion is holding and what it was allowed,
and `61.9 GiB` is what M6's watchdog prints one layer out. The formatter was
`machine_limits/limits.hpp`'s, with all eleven of its callers inside that one
module — the right home while that lasted. **The evaluator must not include
`machine_limits`** (§3.4), so it moved to `system_facts/facts.hpp` as an inline
function: a byte count is that module's currency, every function there answers in
one, and the readable form of one belongs beside them rather than beside a single
consumer. PLAN §6.1 item 3 made the same move with `Bits32` and gave the same
reason.

### 4.7 `FrameRef` had no way to name a user's capsule

DESIGN §9's fourth field has been carried since M5 with no producer, and
`report.hpp` says its first real producer is M9's evaluator. It is — and the
renderer printed **"a capsule this program declared"** for every frame, which is
useless exactly when a stack trace is wanted, because every line reads the same.

A language path can be named from constexpr data; a name the parser interned
lives only in the `words::Words` that interned it. So `errors::Source` gained the
run's numbering beside the file's name and bytes — which is what a diagnostic is
rendered against anyway. **Null is a real case and not a defence**:
`tests/reporter_test` renders synthetic diagnostics with no run behind them.

### 4.8 A command that reports at run time cannot read the cache

`resolve_command.cpp` carries half of this already: a tree read from a `.satc`
has spans into the cache, which has *"no comments, blank lines where the writer
put them, and line 6 of that is not line 6 of the file the user wrote"*.
Measured here: `example/hello_world.satl` is 12 lines and its `.satc` is 11, and
`satellite.return` moves from line 11 to line 10.

**What resolve does about it cannot be done here.** That arm throws the answer
away and parses the source again if the pass fails — affordable, because resolve
is a pure function of a tree. An evaluator can raise a diagnostic at any moment
during a run, and by then the run has happened; from M10 that means output
already printed and from M19 a file already written. *"Run it again from the
source"* is not available to anything that has done something.

So `--compile` and `--call` parse the source. **M10 inherits this for `satl
file.satl` itself**, which is where somebody will first notice the cache not
being used, and the real fix is the `.satc` format's rather than the arm's: a
cached line that recorded which source line it came from would let both be true.
That is M4.5's format and not this milestone's.

### 4.9 And the two cold commands are CHEAPER than the warm one

The one result in `make startup` nobody would have predicted. `--compile
example/frames.satl` is a share of 0.546 ms and `--resolve example/frames.satl`
is 0.635 ms — **on the same program, with the compile doing a whole extra pass on
top of everything resolve does**, and reading no cache where resolve reads one.

The `.satc` is the difference: `--resolve` opens the cache directory, stats a
file, reads or writes it, and hashes the source to name it. Those are syscalls,
and the trie walks a cache saves are not — MILESTONES/M7.md §5 counted them at 28
on this file, far under what a shell loop can see. **A cache that saves counted
work and spends uncounted syscalls can be a net loss on a small program**, and
this is the first row in `startup.rows` that shows it. It is not an argument
against the cache, which exists for programs larger than 273 bytes; it is an
argument for measuring it on one.

### 4.10 The stopping rule was nearly right

`refuse()` cleared the work stack, on the reasoning that an empty stack ends the
loop. It does — **but an arm is not finished when it refuses.** `a + b` pushes
two children, and if the first push reached the ceiling the second still ran,
onto a stack that had just been emptied.

Guarding every push against the run's state would have fixed it and put a load
and a compare on the hottest path in the interpreter. The loop tests it instead,
where there is already a compare, and `refuse()` keeps only the first sentence —
because one event can reach it twice for exactly this reason.

### 4.11 A float cannot be inline, and M15 does not get to decide that

`sizeof(Number)` is 32 and the variant's discriminator is 8, so `Value` is 40
with nothing to spare. DESIGN §8.6 makes a float a bool and **two**
`satellite_number`s — 72 bytes laid flat. So a float arrives behind a handle the
way a list and a map do, and that is a consequence of §8.1's exactness rather
than a choice M15 has. It is written into `value.hpp` because the place it would
otherwise be discovered is a failing `static_assert` with no explanation attached.

### 4.12 `satellite.variable.binary` and `.hex` have a lexer and no milestone

M3 lexes `x00FF` and `b1010`, DESIGN §8.5 specifies them as real types where
*"the width is part of the value"*, and PLAN §8 gives `satellite.variable.binary`
`1 6 5` and `.hex` `1 6 11` to the lexer's milestone and to no evaluator's. M11
is scalars and names bool, number and string; M16 is containers. **Neither claims
these two.** So `satl --compile` on a program with a hex literal in it says so,
in those words, with the milestone column reading *no milestone in PLAN.md §8
owns the value*. A gap named is a gap somebody can close.

## 5. How it was checked

**Three, in increasing strength.**

1. **All nine suites green**, `tests/eval_test` being the new one: 6 sections,
   about 100 check sites over the compile, the arithmetic, the control flow, the
   calls, the depth and the dispatch. Every S07xx row in `errors.def` is raised
   by a real program through the real entry points, which is the rule
   `tests/reporter_test/parsing.cpp` established.
2. **The acceptance programs**, which caught §4.2 where the fixtures did not.
   `satl --call example/frames.satl factorial 10` answers 3628800 and
   `satl --compile example/hello_world.satl` shows the milestone boundary as a
   listing: the console call is a `dispatch` op with an inline cache, and
   `satellite.return(satellite)` is a refusal naming M10.
3. **The depth fixtures, against 8 MiB.** `065-tests.mk` names no
   `machine_limits` among this binary's sources, so nothing raises
   `RLIMIT_STACK`; a 1,000,000-frame recursion answers and an evaluator that
   still recursed would fail rather than pass. **This is the check the whole
   milestone is for**, and §3.4 is why it means something.

**And one assertion that cannot be made any other way.** A `while` loop of
100,000 rounds costs *exactly the same* control stack as one of 10 rounds. The
answers differ and the peak does not, which is NO_LIMITS §2.2's *"a loop costs
zero stack depth"* turned from a sentence about the first satellite into an
assertion about this one.

## 6. What it cost, measured rather than quoted

### 6.1 The evaluator's 2–3×, which is the figure §2.5 was arguing about

**It is a range and not a number, and what decides it is how much work sits
between two pushes.** Two evaluators over the same closure arena, the same
`Value`s, the same arithmetic, both dispatching through one function pointer per
op — so the only difference measured is where the intermediate state lives. Best
of nine, three runs, 2026-09-01, load 0.8:

| workload | control stack | C++ stack | |
|---|---:|---:|---|
| a tight arithmetic loop, no calls | 107.0 ms | 30.0 ms | **3.5×** |
| long expression chains | 107.3 ms | 36.5 ms | **2.9×** |
| 200,000 calls that each return | 120.1 ms | 45.6 ms | **2.6×** |
| **a program shaped like a program** | 343.1 ms | 258.3 ms | **1.3×** |
| 15,000 frames deep | 4.5 ms | 2.9 ms | **1.6×** |
| **20,000 frames deep** | **answers** | **SEGFAULT** | — |

**So 2–3× was a fair thing to have borrowed**, and it is wrong at both ends. It
is the same shape M8.5 found one layer up, where the `.satc` writer paid 1.25×
against the printer's 2.5× *"because it does more work per node, so the walk is a
smaller share of it"*.

**The last row is the answer to the other half of the question.** NO_LIMITS §8
asks whether the cost is *"paid everywhere or only where it is needed"*: the
C++-stack arm dies between 15,000 and 20,000 frames at the default `ulimit -s`,
which is the band §2.4 already recorded for the printers. Where it is needed is
**not knowable before the program runs**, and there is no point at which a
recursive evaluator could hand over to a heap one — it is already holding the
frames it would have to hand over.

### 6.2 One fifth of it came off when it was looked at

The first measurement was **4.2×** on the tight loop. Every binary operator ended
pop, pop, push — three vector operations — where two values becoming one in place
is an assignment and a pop, and the push is the expensive one because it is the
only one that asks whether the ceiling has been reached. `Machine::fold()` and
its unary sibling `set_top()`.

That is 4.2× → 3.5× on the worst case and about 10% off the realistic one, and it
is recorded because **a figure taken before the obvious thing was tried is not
the cost of the design, it is the cost of the first draft.**

### 6.3 Startup, and the image

`make startup STATIC=full`, 2026-09-01, against `startup.rows`' M8 baseline:

    satl                       share 0.239   (M8: 0.199)   +0.040
    satl --compile frames      share 0.546   (new at M9)
    satl --call frames fact    share 0.521   (new at M9)

**Every row moved by about the same amount and the row that moved is the bare
`satl`, which never reaches an arm** — so it is the image again, which is M8's
attribution used rather than repeated. `satl` at STATIC=full went from 1,887,016
bytes to 2,134,224: **+247,208 for twenty-two objects.** A cost paid before a
command is chosen cannot be that command's work.

### 6.4 The tree

`src/` is **133 files and 22,328 lines**, from M8.5's 111 and 18,766. With
`tests/` it is 199 files and 32,121.

**Every file in `evaluator/` is under PLAN §3's 300**, the widest being
`operations_control.cpp` at 299 — which is the first module in this tree written
to the target rather than split down to it afterwards. §3's own argument is that
*"splitting a file after the fact preserves its shape; writing to a target
changes the shape"*, and the shape here is the three-way seam
`abstract_syntax_tree/unparse_*.cpp` and `satellite_cache/write_*.cpp` already
have: expressions, statements, and the walk that calls both.

`make test` went from about 1.4 s to 3.9 s. `eval_test` is 0.51 s of that and the
rest was already there; the 0.51 s is one million capsule frames, a 100,000-term
expression compiled and evaluated, and a runaway recursion filling 8 MiB.

## 7. What it left open

1. **The console, `satellite.main` and `satellite.return`'s three shapes are
   M10's**, and `satl --run` still says so. `--compile` on `hello_world.satl`
   prints exactly what is missing, which is the most useful form that answer
   could take.
2. **`satl file.satl` will not be able to read the `.satc` either** (§4.8), and
   the fix is the format's rather than the arm's. M10 is where somebody notices.
3. **The heap-exhaustion question is narrower and still the author's.**
   NO_LIMITS §8 question 1 is now the only one left in that file, and what is
   left of it is whether M9's shape — *a ceiling on the thing that is growing,
   checked where it grows* — should be copied to M16's list, M8's division and a
   printer's output, or whether the watchdog stays the single answer for
   everything that is not a stack.
4. **`satellite.variable.binary` and `.hex` belong to no milestone** (§4.12).
5. **A peephole pass is not built and is worth knowing about.** A binary
   operator whose two children are both leaves — a local and a constant, which is
   most of a loop body — could be one fused op instead of three, and §6.1's 3.5×
   is where that would show. It is deliberately not done here: PLAN §2.3's list
