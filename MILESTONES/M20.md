## 2. The decisions

### 2.1 Fifty-one numbers, in four sittings

**Thirty-eight on 2026-09-11's second commit** — the arguments subtree and the
three call shapes `1 22 4 4 7`, `1 22 4 5 6` and `1 22 9`. PLAN's entry required
`words.def` and WORD_NUMBERS §2.2 to move together and **the build refused
until two more files did**: `help_lines/nodes.tsv` and the written entries,
because `help_text.hpp` static-asserts one help row per registry node in
registry order. **A registry row is not a registry row until it has a help
line** — M18's machinery holding a later milestone to its own rule.

**Ten on the seventh commit** — `satellite.container.arguments` `1 4 3 1`
through `1 4 3 10`, which the author settled on 2026-09-11. **`1 4 3 0` is
deliberately not minted**: `list()` and `map()` are constructors, and there is
exactly one arguments object per run which the language hands over, so a
program has nothing to construct.

**One on the same commit** — `satellite.variable.string.resolved` `1 6 1 17`.
§2.4.

**And one row was RESPELLED rather than minted**, which is §3.1.

§2.2's counts moved 285 → 296 rows and 282 → 293 numbers; `kNodeCount` 325 →
336, and the words digest `1ef8ec50a203c593` → `03e03c025294f677`, which
invalidates every cached `.satc` on the machine exactly as SATC.md §3 says it
should.

### 2.2 The object is two containers at once, and that is why it has two counts

`length()` is how long the command line is; `count()` is how many entries the
object holds — 3 against 37 on this machine. **The author kept both knowing
`length` appears nowhere else in the language** and that `size` is what the
map, the list and the string all answer to. The reading that makes each one
word is that the object really is two things: every program that takes
arguments writes `for (i = 1; i < args.length(); i = i + 1)`, and a length that
counted the machine's facts would walk that loop off the user's words and start
reading the kernel release as though it had been typed.

**`keys` was the one word the author moved**, from this entry's `names` to the
word `satellite.container.map` `1 4 1 8` already uses for the same idea.

### 2.3 The four command-line rows never build the machine's facts

The thirty-two facts are a function-local static assembled on the first ask
(PLAN's measurement: lazy costs nothing and saves 0.48 ms, 42% of the startup
of a program that never asks). **`length()`, `first()`, `last()` and
`contains(x)` therefore read `body.words` directly and never call
`entries_of()`**, which is the one enumeration `count()`, `keys()`, `has(k)`,
`get(k)` and the printer all share. A program that only walks what it was typed
still pays for nothing.

### 2.4 The live codes could be printed and never read, and one word fixed it

**This is the finding the done-when could not survive.** PLAN asks for a
program that prints `arguments.memory.total`, `satellite.system.memory.total
("mb")` and live code 98 and **asserts all three are the same number**. The
first two are assertable — DESIGN §7.7 settled on 2026-09-09 that they are two
surfaces on the coarse fact and one on the exact one, and `truncate()` is how a
program says which it is asking for. **The third could not be asserted at all.**

A live code is ONE stored character that the machine answers at DISPLAY time
(DESIGN §8.3, §5's render/store boundary), so `"\memtotal".to_number()` refuses
on the placeholder text and `total.to_string() == "\memtotal"` is **false**
while both print `63430`. Six values a program could look at and never use.

**The author was asked and chose to mint the word**:
`satellite.variable.string.resolved` `1 6 1 17` answers the string with its
live codes resolved — the same `live_text()` call `display` already makes, then
re-encoded, so what comes out is an ordinary string every other method works
on. **Every other method still sees the stored codes**, which is why `size` of
`"\threads"` is still 1, and DESIGN §8.3 now says which side of the boundary
each is on.

### 2.5 `min_free_mb` retunes, and the synchronisation design was one word

The row refused until this milestone with a true reason: *"the watchdog reads
its floor from the config's store on a thread of its own, and a live handoff to
it is undesigned"* — a torn read there kills a healthy process. **The design is
a single atomic `unsigned long long`**, written whole by the evaluator and read
once per wake-up by the watchdog. Two words — a flag and a value — would have
brought the problem back in a smaller form, since a reader can take the flag
from one write and the value from another.

**So "not watched" is carried in the same word, and `0` is not it.** The author
settled the pair: `min_free_mb = 0` is a floor of zero, armed and never
crossed; `min_free_mb = "disabled"` stops the watch. The stored word is the
floor **plus one**, which spends one value out of 2^64 on the sentinel — a fact
about the representation, not a limit on what a program may ask for, and the
retune's ceiling says so where it is true. **It is quoted because a bare
`disabled` is a variable name in this language**; the four file modes at S1201
are the same shape and the same decision.

## 3. What building it found

### 3.1 `count` was spelled twice under one receiver, and one answer was silent

**The collision the author's two decisions made without either being wrong.**
`satellite.library.main.arguments.count` `1 14 1 1 9` is v1's `argument_count`;
`satellite.container.arguments.count` `1 4 3 2` is how many entries the object
holds. **Both are reached off `satellite.main`'s parameter**, the object's own
children are asked first, and `argz.count()` therefore answered 3 where the
help line the same milestone wrote promised 37 — *answering the wrong fact
rather than failing*, which is the shape this milestone's own resolver defect
had and the reason it was worth a commit.

**Settled by the author 2026-09-11: `length` is the command line, `count` is
the entries, and `1 14 1 1 9` was respelled.** Nothing renumbered. `1 4 3 1` is
`length` too and answers the same number from the same vector, so what is left
is two rows agreeing rather than one hiding the other — which is the whole
difference between this and what it replaced.

### 3.2 A bad selector had two sentences and only one of them was written

`s.nonsense()` answered S0723 — *"`nonsense` is not a question a
`satellite.variable.string` answers"* — and **`s.nonsense` answered
``` `` is a path satellite has a number for and nothing behind yet```**: an
empty pair of backticks and a false claim, because the bare member arm
dispatched `kNoPath`, which is path number 0. **Pre-existing and general**,
measured against the binary of the commit before this one.

**Found by the arguments object's second road**, which this milestone created:
a name declared `satellite.container.arguments` folds the ten selectors through
`1 4 3`, and `held.machine` — a fact, reachable only off the parameter — is
then a word that type does not have. The S0723 sentence is now a function both
roads reach, and the case where the receiver is NOT a declared name gets
WORD_NUMBERS §1.5's one-hop advice instead of a dispatch of path 0.

### 3.3 `satl --call main` could not find `main`

`satellite.library.main` `1 14 1` **is a node** — it is where §7.7 hangs the
object — so the lookup under `library` succeeds, answers a path no capsule was
ever compiled for, and the search stopped there. Two lines in
`programs/evaluate_commands.cpp` and the same two in the eval_test harness: the
second lookup now runs when the first names nothing **compiled**, rather than
when it names nothing at all.

### 3.4 A member past a leaf fact listed nothing

`argz.machine.threads.to_string()` ran `arguments_member()` with a leaf as the
parent and produced *"the arguments object has no `to_string` on it ... and
is what this build has"*, with nothing between "and" and "is". The advice it
owed was a different sentence entirely — `threads` is a number and the fold
stops at §1.5's one hop — so the resolver now says nothing there and lets the
compiler say that.

## 4. What it left open

- **`satellite.system()` `1 22 0` and `memory.this()` `1 22 4 5 0` still
  refuse.** PLAN's entry settled `memory()` and `swap()` on 2026-09-11 and
  explicitly left these two for the author. `satellite_system/group_map.cpp` is
  the reader either would use.
- **`interpreter.library_path` `1 14 1 1 6 2` and `library_path_source`
  `1 14 1 1 6 3` refuse and name M25**, which is this entry's own split: this
  tree's Makefile has no install prefix, so an answer would be a fact about a
  mechanism that does not exist. Thirty-four of the thirty-six answer.
- **A per-SOURCE laziness is quantified and not taken.** `physical_cores()` is
  303 µs and `/proc/cpuinfo` is 305 of the 0.48 ms, against 6 µs for
  `hardware_threads()` — so `arguments.machine.threads` could be nearly free
  while `cores` and `cpu` stayed expensive. Named with the number attached, and
  the author's call.
- **SATC.md §2 has no reading for "the resolver's rules changed while the
  numbering did not"**, which this milestone's third commit needed and worked
  around by checking every cached file by hand.
- **PLAN §8.2's per-milestone path table is 69 rows stale and cannot be
  patched**, found while this milestone was landing. It reads 227 rows against
  `words_test`'s measured 296, and its own rule is that it is counted
  mechanically rather than read off the prose — so the fix is a sweep somebody
  runs, not an addition somebody guesses. The gap is M19.5's eight, M19.6, and
  M20's fifty-one, and §8.2 now carries the note saying so. **Nothing the
  language does depends on it**: §2.2, `words.def`, `help.def` and `nodes.tsv`
  agree on every build by three separate asserts.
