## 1. What the milestone was

- **`satellite.include(ship)` loads `ship.satl`** from the directory of the file
  that includes it — also written `ship(args)`, `ship.satl` and
  `ship.satl(args)`. At the top of a file, or **inside a capsule** as a statement
  that runs when control reaches it.
- **A spaceship is a namespace.** `ship.setup()` calls its capsule, `ship.box b`
  declares its spacesuit, `satellite.library.ship.total` reads its global and
  `satellite.library.ship.settings.speed` a capsule's declared variable. Nothing
  it declares is reachable bare from outside it.
- **`satellite.capsule.launch name(args) { }`, `1 2 1`** — a capsule that runs
  when its file is included, handed the include's arguments by what they fit.
- **One word, thirteen codes, one new suite.** `words.def` gains
  `CAPSULE_LAUNCH` and two `SAT_BUILT` rows; `errors.def` S0246–S0247,
  S0528–S0530, S0533, S0734, S1601–S1602 and S1604–S1606; `tests/spaceship_test`
  runs the real `satl`.

## 2. The decisions

**Each is the author's, taken in conversation while it was built; PLAN's entry
quotes them.**

### 2.1 A counter per file, and one numbering per run

PLAN's done-when asked for a spaceship's names "numbered from the same counter
the host file used". The author: *"separate files so we can use separate name
counters."* So `parse()` takes a `library` owner and a spaceship's capsules,
spacesuits and globals are defined under `satellite.library.<ship>` — whose
children count from 1 — while the run keeps **one** `words::Words`. That is what
makes the rest cheap: a PathId is still unique in the run, so every file's
capsules live in one table, one op arena and one `satellite.library`, and a call
from one file into another is an ordinary `op_call`.

### 2.2 Loaded once

*"What would be the point of loading them twice?"* None. The loader keys a file
by `realpath`, so an include of a file already loaded — from any file, including
a spaceship including the file satl was given — reaches the same file id. Every
file's globals are set up at the start of the run, a file after the files it
includes; the includes written at a file's top run the first time the file is
included, claimed by an atomic in `Globals` so a thread's walk and the program's
agree; every include runs launches.

### 2.3 The word, and the fit

The author proposed `auto`, then `start`. **`launch`** was chosen because
`thread.start()` already runs a thread and a thread runs a capsule. The rule for
several launches read two ways as first written, and the author settled it:
*"smart arg passing — we look for where the arguments fit"*, then *"match the
arguments first, then run the first launch, then the second launch, in that
order."* op_include therefore asks every launch before running any, refuses
S0734 if arguments fit none, and runs every one that fits in file order. A number
fits a float parameter (the declaration converts it), `nothing` fits anything,
and a spacesuit parameter needs an object of that suit or of one extending it.

### 2.4 An include inside a capsule

*"This is for writing a satellite.include(filename(args)) in the middle of a
capsule."* The parser's S0213 for an include in a block is gone for this one
word; the node is the same Include, and the resolver and compiler walk its
arguments as the capsule's own expressions.

### 2.5 Small decisions taken here, and open to the author

- **The file satl is given runs its own no-argument launches** after its top
  level and before `satellite.main` — running a file is including it with
  nothing. A spaceship's own `satellite.main` is not compiled when it is included.
- **A global of a spaceship reached as `ship.total` is refused** (S0530) and
  names `satellite.library.ship.total`; it could as easily be allowed.
- **An include with no arguments is never refused**, even when every launch
  takes some — a file included for its capsules is a real program.
- **Every file's globals are set up before any file's top-level includes run,
  file 0 included.** Found by §3.3; a program that includes nothing compiles no
  include op, so its top level is unchanged.

## 3. What building it found

### 3.1 A node index read against the wrong tree

The first `cargo.crate box` in `launch.satl` refused with a caret on line 15 of
the wrong file. Construction compiled a suit's field initialisers at each
declaration, and a suit from another file has initialisers in that file's tree.
They are now compiled once, by the declaring file (`Compiler::compile_fields`),
and shared by every construction.

### 3.2 File 0 is a file

An include of the file satl was given, from a spaceship, compiled as "nothing
loaded", because `file_included` answered 0 for both. It answers `kNotLoaded` now.

### 3.3 A global below an include

Two files including each other: alpha's top-level include of beta ran beta's
launch, which read alpha's global declared on the next line — still nothing,
because file 0's top level ran its globals and includes interleaved in file
order. Globals first, everywhere.

### 3.4 One code that nothing could produce

S1603, "two different files are both the spaceship `x`", was written with the
loader and cannot happen: every include looks beside its own file and every file
was found beside the first. The number is left as a gap with a note.

### 3.5 Fourteen more, found by four readers who had not written it

An adversarial review — four independent lenses over the change, and a
skeptic reproducing every finding against `./satl` — confirmed 27 findings,
fourteen defects once duplicates were folded, and refuted one. All fourteen are
fixed and `tests/spaceship_test` §6 holds a clause for each that a program can
show:

- **A spaceship could read and overwrite its includer's globals** through its
  own bare `satellite.library.x`, because the walk fell back to the program's
  `satellite.library` for any name the ship did not declare. A spaceship's
  `satellite.library` is now its own node and nothing else; a chain through a
  spaceship it includes goes to that spaceship's node; file 0 cannot reach a
  spaceship it did not include.
- **`satellite.library.<file 0>.x` did not resolve** from a spaceship that
  included the file satl was given, while S0530 advised exactly that spelling.
- **`satellite.main` called inside a spaceship ran the program's main** — the
  one capsule table has one `1 3`. Refused where it is written.
- **S1602 was asked only of file 0**, so a nested file's own capsule silently
  shadowed the spaceship it included. Asked of every include, against the file
  that wrote it.
- **A file named `system.satl` or `main.satl`** numbered its names under the
  language's `satellite.library.system`/`.main`. Refused as S0241.
- **A subclass object did not fit a launch parameter typed with its parent.**
  A suit parameter now accepts every layout whose parent chain reaches it.
- **`--check` analysed file 0 only**; a ring of spacesuits in an included file
  went unreported.
- **Qualified-type diagnostics** were said twice (a capsule's first lines were
  typed twice, once for the capsule-constant table — the old S0522 double
  report had the same cause), put the caret under the wrong word, and called a
  capsule in type position undeclared (S0533 now).
- **A symlink reached a loaded file under a second name**, which then resolved
  to nothing (S1606), and **a symlinked host looked for its spaceships beside
  the link** rather than beside the file.
- **`~/.satl/satellite.log` recorded a spaceship's warning** against the host's
  path and the spaceship's line.
- **A refusal inside a launch showed no call site** for the include that ran it.
  op_include names itself for the next op_enter's frame.
- **On threads, an include could return before another walk had finished
  loading the file** — measured by the reviewer as iterations that saw the file
  unloaded. The first walk holds a per-file loading access (THREAD.md T2's
  machinery, so a cycle between threads is S1408); 20 runs of 16,000 includes
  on eight threads since saw none.
- **`satl --resolve` refused a correct multi-file program with S0521**, and so
  `--satc` never cached one: a lookup through a spaceship the one-file arm did
  not load is silent now.
- **At the prompt, a typed include with arguments** could not take the session's
  variables, and one whose launch refused was kept and refused again on every
  later line. An include with arguments is a statement of its line; a
  top-level form whose run refused does not stay. And the `1 1` help text
  still said an include cannot go inside a capsule.

The refuted one — a typed top-level include re-running its launches on every
later line at the prompt — is real and is the prompt's own model, which
re-runs every kept top-level form per line; it predates this and is left.

## 4. What it left open

- **`satellite.analyze`**, M25's other half, and its two blockers.
- **An include cannot name a directory**, and a spaceship is found nowhere but
  beside its includer — no library path, no `SATELLITE_LIB_DIR`.
- **`satl --resolve` and `--satc` read one file**: a spaceship's name is known
  there, what is inside it is not, and lookups through it are silent rather than
  refused.
- **At the prompt, a kept top-level `satellite.include(ship)` runs its launches
  again on every line**, because the prompt re-runs every kept top-level form.
- **`make tsan` is still THREAD.md T3's**; the loading access has been run
  under load, not under ThreadSanitizer.
- **A spacesuit from another file cannot be a superclass** — `(name)` is bare.
