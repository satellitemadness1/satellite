# M17 — hello world

**Landed 2026-09-06** (`264a9c8`).

[PLAN.md](../PLAN.md) §8's M17 entry is the specification, and its whole demand
is one clause: *"DESIGN §3 runs, byte for byte."*
[DESIGN.md](../DESIGN.md) §3 is the program, and it says of itself that it
**is** `example/hello_world.satl` — *"byte for byte, comments included."*

This is a **review and not a plan**: what was decided on the way, what building
it found, and what it left open.

    $ satl example/hello_world.satl
    Hello, World!

    $ satl example/hello_world.satl one two
    satl: 2 arguments were given and nothing reads them yet -- `arguments` lands at M20 (DESIGN.md §7.7).
    Hello, World!

    $ satl --satc example/hello_world.satl
    #1.1.1                                   // satellite.include(satellite)

    #1.2 #1.3(#1.4.2<#1.6.1> arguments)      // satellite.capsule satellite.main satellite.container.list satellite.variable.string
    {
        #1.5.1("Hello, World!")              // satellite.console.display
        #1.15.1                              // satellite.return(satellite)
    }

**The first line ran before this milestone started**, and saying so is where the
review has to begin. M16 bound the empty `satellite.container.list` on
2026-09-05 and [M16.md](M16.md) §2.4 records it: *"the S0720 arm in
`run_command.cpp` is gone; `main.parameters != 0` now binds `Value::list(List{})`
into slot 0 and hello world runs."* Its own opening calls that **"M17's
done-when, and it runs today."**

So this milestone inherited a done-when that already passed, and §2.1 is what
that turned out to leave.

---

## 1. What the milestone was

- **The done-when, verified rather than assumed** — `example/hello_world.satl`
  diffed against DESIGN §3's fenced block, byte for byte, and then held there
  by a test rather than by an intention. §2.5.
- **Two of its own four paths, which had never answered.** PLAN §8's path table
  counts M17 at **four**, and its M25 entry names three of them:
  `satellite.include` `1 1`, `satellite.include()` `1 1 0` and
  `satellite.include(satellite)` `1 1 1`. `1 1 0` did not parse. §2.2 — and
  §3.5 is the fourth, which no prose in §8 names at all.
- **The refusal the third row's neighbour gives**, which named the wrong thing
  in the one spelling every document uses. §2.3.
- **The handover**, which PLAN asked this milestone to write down rather than
  leave to be discovered. §2.4.
- **The documents that had gone stale behind M16**, in DESIGN §3, DESIGN §6,
  LAYOUT, `run_command.hpp` and `MILESTONES/README.md`. §3.3.

**Six files under `src/`, seven under `tests/`, one make fragment**, and of the
six only five are code — `programs/run_command.hpp` is a comment that had been
wrong since M16 landed. **No new module, no new word in `words.def`, no new
code in `errors.def`**, which is what a milestone whose subject is a program
that already ran looks like. **Every row it owns was assigned before any of them
could be reached** — `words.def` carried all four on 2026-08-28, when M2
transcribed the numbering, nine days before this.

## 2. The decisions

### 2.1 A done-when that already passes is not a milestone with nothing in it

**The temptation was to write the note and stop**, and the argument against it
is PLAN's own — from two places in §8 that are four hundred lines apart. The
**M25 entry** says *"`satellite.include`'s other three shapes are already
owned"* and names all three as M17's; the **path table** at the end of §8
counts M17 at **four**. A milestone answerable for four rows, two of which do
not answer, is not finished because the file its own entry names happens to
print. **Neither of those two places is the M17 entry**, which is §3.5.

**What separated the two was running the paths rather than the program.** Hello
world writes `satellite.include(satellite)` and nothing else under `1 1`, so
every run of the acceptance file exercises one of the three shapes and says
nothing about the other two. Both were broken. Neither could have been found by
the done-when.

### 2.2 `satellite.include()` `1 1 0` — the numbering was right and the grammar was wrong

**It answered S0231, "expected an expression".** DESIGN §6's grammar read
`include_decl := "satellite" "." "include" "(" expression ")"`, so the empty
form was a parse error.

**And WORD_NUMBERS.md §1.3 uses that exact form to teach the whole numbering**:

> `satellite.include()` `1 1 0` / `satellite.include(satellite)` `1 1 1` …
> **`0` means nothing in that position.** It is a real number in the sequence
> and not a piece of notation, which is why `include()` and `include(satellite)`
> are two different sequences rather than one path called two ways.

and then states the rule that decides which document was wrong: **"a trailing
`0` is written only where a program can actually write the bare form."**
WORD_NUMBERS is the authority over the numbering by its own opening rule, so
**the grammar moved**: `"(" [ expression ] ")"`. DESIGN §6 carries the
correction struck-through rather than replaced, which is the shape that section
already uses for `suit_section`.

**This is the same resolution DESIGN §3 reached on 2026-08-28 and reached the
same way.** The parameter was removed from hello world on **2026-08-27**, on a
misreading of WORD_NUMBERS §1.3's `(0)` as *zero arguments*, and **restored the
next day** when §1.3 settled that the marker means *a node reached both bare and
as a parent*. Both times a document argued against the numbering; both times the
numbering won. **§1.3 has now been the load-bearing citation twice and been got
wrong twice** — once by being read as saying something it does not, and once by
a grammar nobody had compared it against at all. The second is the harder of the
two to notice: **a misreading is an argument somebody made, and a contradiction
nobody checked leaves no trace in any document.**

**What it means is what §1.3 says it means and nothing more.** `include()`
includes nothing, and does nothing, and that is not a courtesy extended to a
degenerate case: a program that asks for nothing to be included has asked for
exactly what it got. DESIGN §1.1's tie-breaker points the same way — a refusal
is owed only where the language cannot honour what was written.

### 2.3 A spaceship's name is the spaceship's, not a variable somebody forgot

`satellite.include(cargo)` answered:

    error S0511: nothing called `cargo` is in scope here -- it is not a
    parameter, not a local declared above this line, and not a capsule this
    file declares

**Every clause of that sentence is true and the sentence is wrong.** `cargo` is
a spaceship name — WORD_NUMBERS §2.2 spells `1 1 2` exactly that way, *"a
user-named spaceship"* — so it was never going to be a parameter, a local or a
capsule, and **no edit to the program could make it one.** The message describes
three fixes, none of which exists.

**The other two spellings were always right, which is how the odd one out was
found.** `include("cargo")` and `include(satellite.console)` reach the compiler
and get S0720 naming M25. Only the bare identifier was diverted, because
`statement_form()` walked into the argument as an ordinary expression and a
`Name` node goes to scope lookup while a `String` node does not. **The spelling
that misbehaved is the one both DESIGN and WORD_NUMBERS use.**

**The fix is to leave the name alone**, and it stays right after M25 lands
rather than being a stopgap: a spaceship is looked up among spaceships, never
among locals. All three spellings now give the same sentence, and
`tests/eval_test/compiling.cpp` checks all three in one loop for that reason —
the boundary is round the **form**, not round the way it happens to be written.

### 2.4 What the slot holds is not what the name reaches

**M16 wrote this down and M17 ratifies it**, because PLAN's M17 entry is where
it was asked for: *"a program written between here and the milestone that builds
§7.7 will ask for `arguments.username` and get an error that no document
predicts unless this milestone writes the handover down. That is the M3/M4
failure caught before it happens instead of after."*

Measured, in the three shapes a program can write:

| written | answers | whose |
|---|---|---|
| `arguments` | `[]` | the empty list M16 bound to slot 0 |
| `arguments.username` | S0720, *"builds it at M20"* | DESIGN §7.7's object |
| `arguments.size()` | S0532, *"the arguments object has no `size` on it"* | §7.7 again, and **not** a list method |

**Both halves are true at once and neither is a stopgap.** The empty list is
what M16 owed the slot; the object is what M20 owes the name. A program that
wants the list passes `arguments` on; a program that wants the machine's answers
waits for M20. **`arguments.size()` is the row worth reading twice** — the value
in the slot is a list and lists have a `size`, and it is still refused, because
resolve routes the name to §7.7 before the value is ever consulted.

**And `example/frames.satl` shows both halves in one program**, which is why it
is named here: it prints, and then stops at line 25 on `arguments.machine.cores`
with M20's number in the sentence.

### 2.5 DESIGN §3 is now held to the file, and a copy is not a guarantee

DESIGN §3 says the reason it is a transcription rather than a description:

> so the two must not be able to drift; the way to guarantee that is for this
> section to be a copy rather than a description.

**A copy is an intention. Nothing compared them.** `tests/parser_test/roundtrip.cpp`
already checked that hello world *prints back* as §3 writes it — but against §3
**transcribed into a C++ string literal in that file**, so DESIGN.md itself was
free to drift from both. **Three places held that program and only one pair of
them was ever compared** — and the pair that was compared is the one that
cannot see a comment, since the check runs through the printer and DESIGN §5.6's
comments are not tokens.

**So the test now reads DESIGN.md**, cuts the fenced block out from under
`## 3. Hello world`, and asserts it IS `example/hello_world.satl`. DESIGN.md is
a prerequisite of the test binary in `make_support/065-tests.mk` — the
arrangement `WORD_NUMBERS.md` has with `words_test`, and for the identical
reason: **editing the authority must re-run the test that checks it.**

**Both checks stay.** The string literal holds the parser and printer to §3; the
new one holds §3 to the file. Deleting either leaves a pair that can drift.

**It was mutation-tested rather than trusted**, §3.4.

### 2.6 What this milestone did not touch

**The no-op condition in `evaluator/compile.cpp` names the two rows that do
nothing rather than the one that refuses**, and that is deliberate. Written the
other way — *refuse unless the path is `1 1 2`* — it would be one comparison
instead of two and would silently start refusing any include row added later.
Written this way, a new row refuses until somebody says otherwise, which is the
direction a language should fail in.

**Nothing was done about the `arguments` object.** M20 owns it, DESIGN §7.7
specifies it, and building a first field here would be the empty-list mistake
inverted — a milestone constructing part of a type another milestone owns.

## 3. What building it found

### 3.1 Every layer of the tree was already built for `1 1 0` except the parser

This is the finding worth keeping. When `satellite.include()` began to parse,
**nothing else had to change to make it work**:

- `words.def` carried `INCLUDE_0` at `1 1 0` — it has since M2 transcribed the
  numbering.
- `shape_of()` matched it at arity 0, because `arity_of("()")` is 0 and always
  was.
- `Resolver::statement_form()` already read `n.a == kNoNode` as **argc 0** — a
  branch that could not be reached, written by somebody following the numbering.
- The `.satc` writer's `form()` already printed a zero-arity row with no
  brackets, which is how `satellite.return()` `1 15 0` is written.
- `satellite_cache/unnumber.cpp` names **this form** as the reason a `0` segment
  may not be skipped on the way back in: *"`satellite.include()` is 1 1 0 — so a
  reader that skipped zero, or treated it as a terminator, would refuse a form
  the writer emits."*

**The writer could not emit one.** A comment in the reader justified itself
against a form no part of the tree could produce — written on **2026-08-30** in
`e9df46a`, the commit that landed the cache at M4.5, and correct and unreachable
for the twelve milestones and seven days between then and here. The registry-and-numbering discipline this tree keeps
means a row assigned in WORD_NUMBERS gets built into every layer that walks the
trie *by construction* — and the one layer that has to be written by hand, the
parser, is where the gap sat.

### 3.2 A wrong constant that was unreachable, and became reachable the same day

`satellite_cache/write_declarations.cpp` asked for the include's shape with the
arity written flat:

    shape_path(words::NodeId::SATELLITE, "include", 1, reserved);

**`1`, not counted.** With no parser able to build an argument-less include the
constant was never wrong; the first tree that could be built would have been
written out as `#1.1.2` — the **spaceship** row — a `.satc` that reads back as a
different program and still parses. It is exactly the class of defect
`satellite_cache/paths.cpp` records from 2026-08-30, where
`satellite.console.input(">>>", target)` was written as
`1.5.1(">>>", target)`, `satellite.console.display`.

**A latent wrong constant is not a bug until something reaches it, and what
reaches it is a fix somewhere else.** It was found by walking the layers in
§3.1 rather than by a failing test, because the failing test could not be
written until the parser change landed.

### 3.3 `MILESTONES/README.md`'s M16 row had been stale for a whole milestone

The index said:

| | landed | |
|---|---|---|
| `M16.md` | **not in this tree** | A review of `prototype/M10`, likewise. |

**while `M16.md` beside it opened `**Landed 2026-09-06** (`1fb1df7`)`** and its
first paragraph says it replaced the draft review. The note moved; the row did
not.

**That is that file's own rule failing in the direction it was not written to
catch.** Its rule is *a milestone with no commit is unlanded or mis-labelled; a
milestone with no note is invisible* — and this was a milestone with **both**,
whose index row still described the file it used to be. An index "holds no fact
of its own" and therefore has nothing that can check it. The only thing that
catches it is writing the row in the commit that lands the work, which is what
M17 does for its own.

### 3.4 The new test was mutation-tested, because a green line proves nothing

[M16.md](M16.md) §3.3 is *"a stale test binary reported `ok`"*, and
`make_support/065-tests.mk` carries the same lesson twice more. So the drift
check in §2.5 was run against five deliberately broken inputs before being
believed:

| mutation | result |
|---|---|
| DESIGN §3's `"Hello, World!"` → `"Hello, world!"` | **FAIL** |
| one extra space of indent on the `display` line | **FAIL** |
| the first `// this is a comment` deleted | **FAIL** |
| `## 3. Hello world` retitled | **FAIL**, and the block-found check fails first and says so |
| DESIGN.md missing | **FAIL**, *"DESIGN §3 is an INPUT to this test"* |

**The third row is the one that justifies the check existing.** A dropped
comment is invisible to the round-trip check twenty lines above it, because the
lexer discards comments (DESIGN §5.6) — so the printed form is identical and
only a byte comparison sees it. DESIGN §3's claim is *"comments included"*, and
that clause had nothing behind it.

**The fourth row is why the heading is checked separately.** A retitled heading
would otherwise make the comparison silently vacuous, which is the failure mode
this whole section exists to refuse.

**The four checks in §2.2 and §2.3 were put through the same treatment**, by
inverting each assertion to the value it would have had before the fix and
confirming the suite went red — because a check written the same afternoon as
the code it checks is exactly the one nobody has ever seen fail:

| assertion inverted to | suite | result |
|---|---|---|
| `include()` resolves to `1 1 2` | `resolve_test` | **FAIL** |
| `include(cargo)` resolves to `1 1 0` | `resolve_test` | **FAIL** |
| `include()` writes `#1.1.9` | `satc_test` | **FAIL** |
| the capsule beside `include()` answers `9` | `eval_test` | **FAIL** |

**`make test` stops at the first failing suite**, which is a property of the run
list being an ORDER — so the last two were reached by running their binaries
directly. Worth knowing before somebody inverts two checks and concludes from
one failure that the other never ran.

### 3.5 One of M17's four paths is named by no sentence in PLAN §8

PLAN §8's path table makes a claim about itself: **"All 227 rows are named by
exactly one milestone above, counted mechanically against §2.2 rather than read
off the prose."** M17's cell reads **4**.

**Three are named in prose, and they are named in M25's entry rather than in
M17's** — *"`satellite.include`'s other three shapes are already owned and this
milestone takes only the fourth. `satellite.include` `1 1`, `include()` `1 1 0`
and `include(satellite)` `1 1 1` are M17's."* A milestone's own entry does not
list its paths; the entry four hundred lines below it does, in passing, while
explaining what it is *not* taking.

**The fourth is `satellite` `1` — the root, and the runtime singleton — and
nothing says so.** WORD_NUMBERS §2.2's first row is the only place it appears,
with no milestone anywhere. It is M17's by elimination over the program: every
other path hello world writes is claimed by name — `capsule` `1 2` by M7, `main`
`1 3`, `console.display` `1 5 1` and all three `return` shapes by M10,
`container.list` `1 4 2` by M16, `variable.string` `1 6 1` by M11 — and PLAN
says outright that "M1, M2, M4.5, M5, M9, M21 and M22 hold none."

**This milestone takes the row and does not renumber anything**, which costs
nothing because the count was already 4. **What is worth recording is how it
was found**: by trying to write the four rows down in this note's §1 and being
able to name only three. A table counted mechanically and a prose that names
things one at a time will agree on the total long after they have stopped
agreeing on which. The claim "named by exactly one milestone above" was true of
226 rows.

### 3.6 Only one program in `example/` writes any of this

`example/hello_world.satl` is the file every milestone since M1 has been aimed
at, and it writes `satellite.include(satellite)`. Of the language's four include
rows, the acceptance suite reaches **one**. Two were broken. That is not an
argument for more acceptance files — it is the argument PLAN §8 already makes
for a **test section** per milestone, and it is why M17's checks are in
`parser_test`, `resolve_test`, `satc_test` and `eval_test` rather than in a new
`.satl` file.

## 5. Startup

**Taken 2026-09-06**, at `STATIC=full`, load 1.34, best of 5 runs of 200.
`make_support/startup.rows` carries the table and the argument; this is what it
found.

**Every row moved and seven were flagged**, and the flagged ones include the two
that run no arm at all:

| | share | was | delta |
|---|---:|---:|---:|
| `satl` | 0.338 | 0.234 | **+0.104** |
| `satl --version` | 0.340 | 0.232 | **+0.108** |
| `satl example/console.satl` | 0.577 | 0.473 | **+0.104** |
| `satl example/variant.satl` | 0.724 | 0.612 | +0.112 |
| **`satl example/hello_world.satl`** | **0.589** | — | — |

**It is real and it was checked before being written down.** Two independent
invocations of the harness on the same build gave `--version` at 0.340 and
0.347 — a spread of **0.007** against a delta of **0.104**. Load was 1.34 and
1.26 against the baseline's 1.00, which is the one confounder not controlled
for and is nowhere near large enough to move a row by a fifth.

**And it is four milestones wide, which is the finding rather than the number.**
M13, M14, M15 and M16 all landed without running this target. The bill arrived
at M17, and **M17 is not where it was spent** — this milestone added five source
files and no module. §9's rule going unrun is the exact failure
[M6.md](M6.md) §9.1 records, where a 34x regression sat undiscovered behind
three milestones; the difference is that this one was caught at 0.104 rather
than at 34x, and the cost of the delay is that **nobody can now say which of the
four it belongs to.**

**What the evidence supports is "the image", and no finer.** `satl` at
`STATIC=full` is **3,837,608 bytes** against the **1,887,016** `startup.rows`
records at M8 — slightly more than doubled, across M9's evaluator and value
model, M10's console, M11's scalars, M12's variant, M13's clock and dice, M14's
reader, M15's float and M16's containers and search power. That is real code.
`satl` and `--version` choose no command, so what they pay is the loader mapping
a bigger image, which is the same attribution M7 recorded for +0.011 and M8 for
+0.018.

**The one trap that would have made it a mistake was checked and is not
present.** `048-static.mk`'s rule is that the static figure *"survives only while
nothing touches `<iostream>`, `<fstream>` or `<sstream>`"* — an `ifstream`
reader once put 1.4 MB back at M3. A `grep -rl` over `src/` for all three
returns **nothing**. The doubling is growth, not a regression in discipline.

**The prediction, and where it was wrong.** Written above before the measurement
and left in place: *"at or just under `console.satl`."* Measured **0.589 against
`console.satl`'s 0.577** — just **over** rather than just under, by 0.012, which
is under the harness's own run-to-run spread. **The neighbourhood was right and
the sign was wrong, and the sign is the half a prediction is for.**

**What the row is actually worth knowing for**: hello world and `console.satl`
are the same program plus one `satellite.container.list` constructed and bound
to slot 0, and they are 0.012 apart. **Binding M16's empty list costs nothing
measurable**, which is the claim §2.4 could not make without this row.

## 6. What is left open

1. **`arguments` as an object is M20's, and nothing here anticipated it.** §2.4
   is the handover written down; the seven fields DESIGN §7.7 lists are not
   built and were never this milestone's.
2. **`arguments[0]` has no answer.** DESIGN §7.7 leaves it open in as many
   words — *"nothing yet says whether index 0 is the program name, the current
   directory, or the first thing the user typed"* — and the empty list this
   milestone hands over means no program can yet ask.
3. **Command-line arguments are accepted and dropped**, with one line on stderr
   saying so. That is M10's arrangement and it stays until M20 gives the list
   something to hold; the alternative — filling the list M16 built with the
   words after the filename — would be **guessing at item 2's answer**, and the
   language does not guess.
4. **`+` has no string reading, and `example/advanced.satl` stops on it.**
   Measured on 2026-09-06: line 10, S0711, `"YOU ENTERED: " + local_user_input`.
   DESIGN §6.6's table gives `+` to arithmetic and gives no operator a string
   reading. **The language is not missing concatenation** — `append(x)`
   `1 6 1 14` is one of M11's sixteen string methods — so what is open is
   whether the *operator* gets the reading, and that is a language decision this
   milestone has no standing to take. **Named here rather than filed**, because
   an acceptance file written before the language existed is stopped by it, and
   the next person to write a second satellite program will reach for `+`
   before they reach for `.append`.
5. **PLAN §1's running account stops at M12.** M13 through M16 landed without a
   paragraph in it. M17 added its own and said so rather than backfilling four
   milestones it did not build.
