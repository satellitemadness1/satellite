## 3. The three blockers, and a fourth thing no document settled

PLAN §8's M6 opened *"Blockers, all three of them §4.5's own and **none of them
this milestone's to take**"* — and all three had to be taken, because each one is
load-bearing for a clause of the done-when. §4.5.3 and §4.5.4 now carry the
answers where the questions were asked; this is the argument for each.

### 3.1 A unit is part of the value, and a bare number is refused

§4.5.4 asked *"what unit is `MEMORY_MAX` in"* in one line: **61.9 GiB and 64.9 GB
are the same memory.** That sentence is the answer as well as the question. Any
choice of a default unit makes the file say something its reader cannot check —
`MEMORY_MAX=48` is either 51,539,607,552 bytes or 48,000,000,000, a difference of
3.5 GB, and nothing in the file distinguishes them.

So the unit is written down: nine of them, `B` / `KiB` / `MiB` / `GiB` / `TiB` for
powers of 1024 and `KB` / `MB` / `GB` / `TB` for powers of 1000, matched without
regard to case because somebody typing a config is not choosing between `GiB` and
`gib`. A bare number is **S0805**, whose sentence quotes the number back in both
spellings so the fix is a copy rather than a lookup.

**Whole numbers of units only**, which is the part that took a second pass.
`61.9GiB` is 66,461,528,883.2 bytes; rounding it silently gives a ceiling nobody
can predict the behaviour of, and there is no unit small enough to make every
fraction exact. Writing the next unit down is exact by construction, so that is
what **S0809** asks for — and it is its own row rather than S0804's, because *"is
a whole number"* would be true and would not name the fix.

**The default is the whole machine.** §4.5.4 asked whether it should be a fraction:
50% is generous for a parser and absurd for the thing QUAD.md exists to run, and
satl has never seen the program. A fraction is a policy invented about work that
has not happened, which is exactly the hidden threshold DESIGN §1.1 refuses. The
machine's own `MemTotal` is the one bound that is true without knowing anything:
past it the run is not slow, it is over.

**And the machine wins.** A file asking for 128 GiB on a 61.9 GiB machine is
holding satl to nothing — the OOM killer arrives first and the watchdog never
speaks — so the value is clamped. **Clamped and SAID**: `satl --limits` prints
that row's origin as *"the machine, over the file"* with the file and line, so the
person who wrote 128 GiB finds out. Clamping quietly would have been the same
failure the bare number is.

### 3.2 The file seeds the namespace, and it holds two kinds of line

§4.5.3 described the arrangement and then said *"Not yet decided"*. It is decided:
the file is read once, at startup, its values land in the dials, and **nothing
reads the file again**. One authority at run time, one place to edit at rest.

**What the section was missing is that the file holds two kinds of line**, and
the spelling is what tells them apart:

    THREAD_COUNT   CORE_COUNT   MEMORY_MAX        machine settings, SHOUTED
    division_digits  max_depth  min_free_mb  float_digits     dials, lower case

The upper-case three are in **no numbering at all** — no `satellite.` path names
them, and a program cannot read or retune them, because what they configure is the
process and not the language. The lower-case four *are*
`satellite.library.system.*`, `1 14 2 1` to `1 14 2 4`, which is the half §4.5.3
was written about. Reading one line of the file tells you which you are looking
at.

**And the dial names come out of `words.def`.** `config_internal.hpp`'s
`dial_name()` reads `kNodes[node].text`, so `min_free_mb` is spelled once in this
tree and the config file's spelling is the language's by construction. Writing the
four names again would have been a place for the two to disagree, and the
disagreement would have looked like a config file with a typo the user did not
make.

**Only `min_free_mb` has a meaning**, which is PLAN M6's own constraint: *"the
node and the storage land here."* The other three are stored, settable from the
file, printed by `satl --limits` beside the milestone that will read them, and
interpreted by nothing. A `Dial` therefore has an **unset** state that is not
zero — because a default for `division_digits` would have been M8 deciding what a
division does, three milestones early.

### 3.3 A setting may differ from a fact, and M20 builds one reader

§4.5.4's third question decides *"whether M20 builds one reader or two"*. **One.**

`THREAD_COUNT` says what satl may use and `satellite.library.main.arguments.machine.threads`
`1 14 1 1 1 3` says what the machine has. They are allowed to differ — asking for
fewer threads leaves the machine room, asking for more is oversubscription, which
is a real technique for work that blocks on a disk. What makes the rule cheap to
keep is that **`THREAD_COUNT` is in no numbering**: there is no path that reaches
it, so no program can get the setting when it asked for the fact, and no rule has
to be written to stop one. `satl --limits` prints both side by side, which is the
visible form of the difference rather than a promise about it. The same answer
settles `satellite_string`'s code 97 (SCRATCH.md/PORTING.md §3): it is the fact.

**MEMORY_MAX is clamped and THREAD_COUNT is not, and the asymmetry is the point.**
Asking for more memory than exists is not a technique; it is a number that cannot
happen.

### 3.4 The exit status is 4, and PLAN's own done-when says 2

**This is a deliberate departure from what PLAN M6 asks for, and it is written
here at length so the author can overrule it in one line.**

The done-when says the watchdog kills the process with *"exit status 2"*. That is
v1's `_exit(2)` carried forward. In this tree, `programs/opening.hpp` has said
since M1 that 2 is `EXIT_USAGE` — *"the command line did not name something satl
can do"* — and that file exists, in its own words, *"so that two arms cannot
disagree about what a given failure is worth."*

A watchdog kill is the opposite of a usage error: the command line was right, and
the machine ran out. A script that tests for 2 would report a memory ceiling as a
typo. The enum's own rule decides it — *"the numbers here are assigned by what a
failure IS and not by the order they were invented in"* — so `EXIT_LIMIT = 4`,
the next free number, with a meaning nothing else had.

**`EXIT_MALFORMED` was widened rather than joined by a fifth status.** It said
*"the file is not a satellite program"*; a `satellite_config.ini` that will not
read is now the second kind of file that reaches it, and from satl's side they are
one failure: it was handed a file, the file is not what it has to be, and nothing
was done. 1 is what every compiler in the world returns for a file it could not
read.

## 4. What building it found

### 4.1 254 nodes is not under a 170-line floor

**The done-when's own reason is wrong, and the clause it is the reason for is
right.** It says `satl --words` walks single-threaded *"because 254 nodes is far
under the 170-line floor"* — and 254 is more than 170.

The ~170 is §4.5.1.1's **second-batch crossover**, measured in satellite-rooted
**source lines being interned**: below it, waking 24 parked threads costs more
than doing the work. `satl --words` interns nothing. It prints a `constexpr`
table, and §4.5.1 settles that case separately and far more strongly:
*"threading the table at startup is a guaranteed loss ... the table is `constexpr`
and lands in rodata, so there is no startup work left to thread."*

So both halves of the clause hold and only the reason moves, and `walk_note_text()`
prints the corrected one — because a sentence in the output that gave the wrong
reason would be worse than none, in exactly the way M5's *"site raising the wrong
row"* is.

### 4.2 The pool starting always needs a flag that does not exist yet

M6's last clause is *"the watchdog fires ... and the process gone within a second
of the threshold being crossed"*, and **nothing satl does today lasts a second.**
The longest command in the tree is `satl --words` at about 0.8 ms. There is no run
for a once-a-second thread to fire during, so the clause could not be met at all
without something that holds the process open.

`satl --watchdog [file]` is that, and it is in the usage list rather than hidden,
because a demonstration harness nobody can find is one that stops being run. Its
tenants arrive at M10 (a running program) and M22 (the prompt), and it stays
useful after them as the way to watch a long run's ceiling without being the run.

### 4.3 `hardware_concurrency` is the wrong question when the pool is unconditional

v1's `hardware_threads()` answered `std::thread::hardware_concurrency()`, which on
glibc is `sysconf(_SC_NPROCESSORS_ONLN)` — the machine's online CPUs, whatever
this process is allowed to run on. That was harmless in v1, where nothing spawned
a pool. §4.5.1.2 makes the pool start **on every run**, and under
`taskset -c 0-3` the ported reader would spawn 24 threads onto 4 CPUs, for the
life of the process, every time.

So it asks `sched_getaffinity` instead. **That is a third reading of one number
that §4.5.4's setting-versus-fact split does not have a name for**: not what the
machine has, and not what satl may use, but what the OS will let *this run* use.
It is the right fallback for the setting precisely because it is the smallest
honest number, and PLAN §4.5.1.2 now records it beside the fallback rule.

`physical_cores()` is new — v1 never needed a core count — and it counts distinct
`(physical_package_id, core_id)` pairs from `/sys`. **Never threads ÷ 2**: that is
right on this Xeon and wrong on every machine without SMT, and §4.5.1.2 already
refuses the same arithmetic in the other direction.

### 4.4 A leaked pool is the correct pool

`pool.cpp` allocates once with `new` and never deletes, and detaches every thread.
Both directions of the obvious alternative are worse:

- a destructor that **joins** puts that cost on the exit path of every run,
  including `satl --version`, to tidy up threads the kernel is about to reclaim;
- a **static** pool destroyed at exit is the classic exit-time crash, because
  static destructors run while detached threads are still awake.

Leaking makes the second impossible — there is nothing to destroy, so there is no
window — and the first unnecessary. It is also the shape v1's watchdog already
had.

**And the process routinely exits while the builder is still building**, which is
not a corner but the ordinary case: `satl --version` finishes in ~0.6 ms and the
pool takes ~0.59 ms to spawn. `exit()` from the main thread tears down the whole
thread group; nothing here is read after `main` returns, so nothing is left half
written.

### 4.5 `std::thread`'s constructor throws, on a thread with nothing above it

The obvious batch runner splits the work, wakes the pool, does its own chunk and
waits. `run_over()` instead keeps taking chunks until there are none left, so
with zero workers awake it does all of them and waits for nothing — and §7.3
records that the mutation which removes that loop does **not** hang the suite,
because a worker created after the wake still sees a new generation and takes
what is left.

**What building that mutation found is a real defect one line away.**
`std::thread`'s constructor *throws* `std::system_error` when `pthread_create`
fails — `ulimit -u`, a cgroup pids cap, a machine out of memory — and `build()`
runs on a detached thread with no handler above it, so letting it escape is
`std::terminate`: satl killed at startup, silently, because it could not make its
twentieth thread. It catches now. That is also the case the keep-taking loop is
actually for: a pool that can never be filled, where waiting for a chunk nobody
will take is a hang and not a delay.

**The chunk is rounded up and the count is derived back from it**, not the other
way round. One chunk per thread, rounded up, gives 10 units over 9 threads as 9
chunks of 2 — and the last four begin at or past unit 10. `tests/limits_test/pool.cpp`
runs a batch of exactly `kFloor` units for that boundary.

### 4.6 `61.9GiB` answered "`.9GiB` is not a unit"

The first `size_value()` scanned digits, stopped at the `.`, and asked what unit
`.9GiB` is. **True, useless, and pointing at the wrong half of the value.** The
fraction is caught before the suffix is looked at, so the caret lands under `61.9`
and the sentence names the fix. Found by `tests/limits_test/reading.cpp`, which
asserted the code and got a different one — which is the check MILESTONES/M5.md §5
says a message registry needs and is the first time it has caught something.

### 4.7 The reporter had no `unsigned long long`

`errors::detail::as_text` had overloads up to `unsigned long` and no `long long`.
A byte count is `unsigned long long`, so every M6 call site was *ambiguous against
five candidates* rather than picking the obvious one. Added as a pair — the signed
one has no caller — so that the next site to hand it a 64-bit value does not come
back here.

## 5. The finding: the pool is invisible to every command satl has

**On this machine, `satl --words` reproducibly finishes with 4 of 24 threads
built.** `satl --limits` finishes with 0. Measured 2026-08-30, and it is the same
number run after run.

*(Re-measured 2026-08-31 after §9.4: `--words` is 3 of 24 and `--limits` is 14 to
19, where it had been reproducibly 0. **The pool did not get faster — it starts
earlier**, because `limits.cpp` no longer spends 0.42 ms reading the machine
before it reaches `pool::start()`. The numbers below are as they were taken and
the finding is unchanged; §9.4 says which of the sentences under it moved.)*

That is not a fault, and `satl --limits` and `satl --words` both say so in the
line that prints it. It is **§4.5.1.1's ramp seen from outside**: the pool costs
~590 µs to finish spawning and satl's longest command is ~800 µs, of which the
first ~600 is the process starting. The pool is never warm while anything is
happening.

**PLAN already contains this conclusion and had not put a number on it.** §4.5.1
says *"the pool does nothing for a program that threads exactly once, and that is
the common case this section was reasoning about"*, and §4.5.1.2 accepts that on
the strength of a different argument entirely — that the pool's real tenant is the
**running program**, which does not exist until M10. Both are right. What this
milestone adds is that the gap is total rather than partial: there is no command
in this tree today for which the pool's warmth is worth one microsecond, and the
first one is two milestones away.

**Three things follow, and they are why this section is not a complaint.**

1. **The decision is unchanged and correct.** §4.5.1.2's argument was never about
   parse time — *"a size trigger predicts parse cost and is therefore the wrong
   trigger"* — and its cost table is what this milestone had to honour: 1–3% of
   startup for a program that never threads. **The cost table is the part that
   did not survive being measured**: the pool and the watchdog are 0.14 ms, which
   is 22% of a pre-M6 startup and not 1–3%, because the 1–3% was a ratio against
   §4.3's *dynamic* 1,750 µs and this binary is static. §9.1 has the numbers and
   PLAN §4.5.1.2 now carries the correction. The decision stands on its own
   argument, which was never the ratio.
2. **`parallel_for` still does not exist**, in no numbering, no document and no
   milestone, including this one. PLAN M6 says naming it is the honest form of the
   dependency, and `pool.hpp` names it again: `run_over()` is the C++ shape that
   construct will be built on, not the construct.
3. **So `tests/limits_test/pool.cpp` is the pool's only caller in the tree**, and
   that is said out loud rather than left to be noticed — the way 040-sources.mk
   had to say it about `satellite_random`. A batch runner nothing has ever run is
   a batch runner that does not work, which is the argument `reporter_test` makes
   for rendering a call stack no pass produces.

## 6. What is left open

1. **`main.cpp` is 427 lines**, up from 348, and 127 over the target PLAN §3 asks
   a file to be built toward. M6 split `programs/limits_command.cpp` out on the
   seam M4.5 used for `--satc` and M5 for `--check`, which took the growth from
   +79 to +49 rather than removing it. **The seam that would take it under 300 is
   real and is not M6's**: the arms that DUMP a registry (`--words`, `--errors`,
   `--limits`) and the arms that read a FILE (`--tokens`, `--unparse`, `--satc`,
   `--check`) are two subjects, and splitting them is a reshaping of M2 through
   M5's arms rather than of this milestone's. Named here rather than taken, which
   is the answer M4 gave for `unparse.cpp`, M3 for `lexer.cpp` and M2 for
   `authority.cpp`.
2. **The installer does not write a `satellite_config.ini`.** §4.5.4 called it the
   natural author and M6 built only the reader; PLAN §4.5.4 now says why. What is
   still undecided is §5's question and not this one: a file the installer writes
   and the user then edits is a file `--uninstall` must not delete blindly, and
   §5.1's `rmdir`-never-`rm -rf` rule has to answer for it.
3. **`parallel_for` is unowned.** §5 above; unchanged by this milestone and now
   named in three places instead of one.
4. **The dials are integers and the language's are `Number`s.** M8 brings
   arbitrary precision, and `division_digits` is its dial — so the storage here
   will have to widen or the reader will have to convert. `Dial::value` is
   `unsigned long long` today and that is a placeholder, not a decision.
5. **`satl --watchdog` has no way to stop cleanly except an interrupt**, and there
   is no signal handling anywhere in this tree yet. M22 owns the interrupt path
   (`run_emergency_exit_hook`'s registrar is the line editor's raw mode) and it
   inherits this too. **The status a caller actually sees is 130**, measured
   2026-08-31 against the installed binary — `watchdog.hpp` said `EXIT_FINE`
   until that day and §9.3 is what found it.
6. **The watchdog wakes once a second and that period is not configurable.** It is
   the one number in §4.5.2 that nothing in the file can set, and no document has
   asked for one; recorded so that the absence is a decision.
7. **A config in the working directory is deliberately not read**, and that means
   there is no way to test a config against a program without `--limits`. When M10
   can run a file, `satl --limits <config> <program>` is the shape that will be
   wanted and it does not exist.
8. ~~**`facts::physical_cores()` costs 0.42 ms on every run and only `satl
   --limits` reads what it answers.**~~ **CLOSED 2026-08-31, and the fix was not
   the one this item proposed** — see §9.4. It named the seam as "read the fact
   where it is printed rather than where `Held` is filled", which is a
   workaround for the real problem one level up: `limits.cpp` filled every
   setting in from the machine before opening the file **because the file had no
   way to say "the machine"**. `satellite_config.ini` says it now —
   `CORE_COUNT=arguments.machine.cores`, DESIGN §7.7's own pairing — so there is
   no order left to invert. satl's own share of startup is 0.168 ms, down from
   0.620, and `satl --version` opens no files at all.
9. **Nothing re-measures startup, so §9.1's finding was three milestones late.**
   M4, M4.5 and M5 landed without one and the rule that asks for it is a line in
   PLAN §9 with no target behind it. A `make startup` that printed the table
   would be the shape; it is not built, and it is not this milestone's.

## 7. What the test proves, and the mutations that prove the test

`tests/limits_test/` is **107 check sites in four sections**, and the header says
what each of M6's halves is checkable *by* — including the one that is not.

**`section_facts` is the unusual one and it says so at its own top.** Every suite
before this has an authority to be wrong against: `words_test` opens
WORD_NUMBERS.md, `parser_test` reads a grammar. Here the authority is `/proc`,
which is also what the code under test reads — so an assertion that
`hardware_threads()` equals `nproc` is two readers of one file agreeing, and it
would pass on a machine where both were wrong. What is asserted instead is the
**relationships**, which are properties of a machine rather than of a file: cores
never exceed threads, used plus available is total exactly, a resident set is
smaller than the machine, `RLIM_INFINITY` answers *unknown* and not a large
number.

**The watchdog is not in the suite, and that is the one gap worth naming.** Its
proof is a process that dies, which a unit test cannot assert without forking a
binary and waiting a second. §2 above is that proof, run by hand: `1.003s`, exit
4, one line on stderr. What the suite *does* check is everything the watchdog
reads.

caught, one hung nothing and eight went straight through**, and the eight are
worth more than the five — four of them were expected to pass and four were not,
and each of those four exposed an assertion that was weaker than it read.

### 7.2 The four that were closed, and what each assertion had been worth

**These four are the reason this section is longer than M5's.** Every one of them
read like a real check and was not one.

- **`used + available == total` survives reading one row three times.** `Mem` is a
  prefix of `MemTotal`, `MemFree` and `MemAvailable`, so dropping the colon makes
  every key answer `MemTotal` — and then `available == total`, `used == 0`, and
  the sum still holds exactly. The assertion that sees it is
  **`available < total`, strictly**: a running Linux is resident in some of its
  own memory, so equality means two rows were read as one.
- **`>= first` is precisely what a cached answer satisfies.** The residency check
  allocated 4 MiB and asserted the figure had not gone DOWN, which is the one
  thing a frozen number cannot do. It now touches every page — allocating is not
  residency — and asserts strictly greater.
- **The `RLIM_INFINITY` arm never ran.** This machine's soft stack limit is 8 MiB,
  so deleting the arm entirely left the suite green over the branch that matters
  most: M9's depth ceiling comes from this number (DESIGN §7.5) and believing the
  word `unlimited` would put the guard past the cliff it exists to stop. The test
  now raises the soft limit to the hard one, asks, and puts it back — and says out
  loud when it cannot, because a machine with a capped hard limit genuinely
  cannot reach that arm and a silent skip is how a suite goes green over ground
  it never covered.
- **The clamp lives in `begin()` and every assertion stopped at `read_config()`.**
  A version that clamped the value and forgot to mark the row `Clamped` was
  invisible, which makes §3.1's whole argument — clamped *and said* — untested.
  `section_examples` now calls `begin()` on a file asking for 1024 TiB and checks
  the origin, the value and the path.

### 7.3 The three that stand, and why they are not gaps to fix

- **A caller that takes one chunk and waits does not hang here**, and the header's
  first draft claimed it would. It is safe whenever the workers eventually
  arrive, because a worker created after the wake still sees `generation != mine`
  and takes what is left. The case it is actually wrong for is a pool that can
  **never** be fully built — `pthread_create` failing on `ulimit -u` or a cgroup
  pids cap — which a suite cannot arrange for itself. **Building the mutation is
  what found the real defect next door**: `std::thread`'s constructor *throws* on
  that failure, on a detached thread with no handler above it, so satl would have
  died at startup with no message because it could not make its twentieth thread.
  `build()` now catches, a pool that cannot be filled is a smaller pool, and
  `run_over()`'s keep-taking loop is what makes a smaller one correct rather than
  merely slower. What the suite gained instead is a batch run **before**
  `parks_fully()`, which is satl's real situation and was not covered at all.
- **Deriving the chunk count instead of the chunk size is unreachable** while the
  floor is 170 and a pool is tens of threads: a chunk can only begin past the end
  when there are more chunks than units, and `run_over` is never entered below
  170 units. The derivation is still the right way round and it becomes reachable
  the day `kFloor` drops below `THREAD_COUNT + 1`. Recorded rather than tested,
  because a test for it would have to lie about the floor.
- **`dial_name()` returning a literal cannot be caught from here**, because the
  literal agrees with `words.def` today. The check that would see it is *renaming
  the node* — which is what `words_test` does for the numbering by reading
  WORD_NUMBERS.md, and there is no equivalent authority for a spelling that a
  test could read instead. It is the same shape as M2's finding that a deleted
  row silently renumbers its siblings, and it has no cheap answer.

   and the wrong thing to have written down. §6.5 owns the handler that would

3. **`limits.cpp`'s `found_config_path()` was headed "R_OK AND NOT F_OK" over a

### 9.4 The config can name the machine, and that is what the 0.42 ms was

**Written 2026-08-31, after §9.1 and on the author's reading of it.** §6.8 had
recorded the cost and proposed a workaround — read `physical_cores()` where the
`CORE_COUNT` row is printed rather than where `Held` is filled. The author read
that and said the order itself was the bug:

> *you have that backwards then, machine first, then file, so it's broken on
> purpose … if the file says `CORE_COUNT=arguments.machine.cores` then it goes by
> that, if it holds a number there, then it goes by that*

**That is DESIGN §7.7, which had said it since before M6 was built.** *"`arguments.machine.threads`,
`arguments.machine.cores` and `arguments.memory.total` are the same numbers as
`THREAD_COUNT`, `CORE_COUNT` and `MEMORY_MAX` in the configuration … Three ways
to ask, one place that knows."* The three paths are numbered — `1 14 1 1 1 3`,
`1 14 1 1 1 1`, `1 14 1 1 2 1` — and have been in `words.def` all along. **The
configuration was the one of the three surfaces that could not spell its own
half of the pairing**, and `limits.cpp`'s "machine first, then file" was the
workaround for that: fill everything in from the machine, then let the file
overwrite what it names. The comment at the top of that file argued the order was
what made a one-line config change one thing. It was, and it was a workaround
being defended as a design.

**So the file says it.** A machine setting's value is a number or the path that
names its fact — one path each, all six spellings of `arguments` (`arg`, `args`,
`argz`, `argument`, `arguments`, `argumentz`), and the bare form rather than the
rooted one because that is what a program writes. A dial takes no such value and
the line is the same line: there is no fact called `division_digits`.

| the file says | `satl --limits` prints |
|---|---|
| `CORE_COUNT=12` | `12` — `the file, …:31` |
| `CORE_COUNT=arguments.machine.cores` | `12` — `the machine, named by the file, …:31` |
| *(no line)* | `12` — `the machine` |

**The second and third rows hold satl to the same number and are not the same
thing**, which is why `Origin` has four values and not three. Both read the
machine; one of them is a decision somebody wrote down, and *"what is satl
holding to"* and *"who decided that"* are the two questions this column exists
to keep apart.

**Nothing is read from the machine until something asks for the value**, and
that is what actually returns the 0.42 ms. It is not a cache — `system_facts`
still refuses to cache anything, for the reason its header gives — it is that
`Setting::value()` is a function and a startup that fills nothing in has nothing
to fill in.

```
                       before        after
satl --version        1.172 ms     0.724 ms      files opened: 50 -> 0
satl --limits         1.899 ms     1.462 ms
satl's own share      0.620 ms     0.168 ms
```

**What is left is 0.14 ms of pool builder and watchdog** — PLAN §4.5.1.2's
decision costing what §4.5.1.2 decided to spend — and about 0.03 ms of
everything else. It is still 9× M3's 0.018 ms and every microsecond of the
difference is now a thread that was started on purpose.

**`satl --limits` kept 0.42 ms of its own, separately.** It was asking the
machine for the same three facts twice: once for the settings block and once for
the machine block underneath it. `dump.cpp` reads each once now, which is less a
saving than the difference between reporting a machine and reporting it from two
different instants.

#### What it cost to build

**One new row, S0810**, and it is a different sentence from S0804 for the reason
S0809 is: the sentence has to name the fix, and here there are two fixes because
there are two things the value may be. `CORE_COUNT=twelve` could have meant a
number or it could have meant the machine, and *"is a whole number"* alone sends
somebody to look up a core count they did not want to write down. It cannot be
raised from `example/broken_config.ini` — all three machine settings are spent

S0806, S0809 and S0891. **S0804 is the dials' row now**, and only theirs.

**The suggester caught a trap that `nearest_key()` hides.** `errors::distance()`
is **capped**: it returns `kTooFar` for anything at or past it rather than the
real figure. `close_enough(4, 23)` is true — one edit plus one per four
characters — so testing `close_enough()` alone against a candidate as long as
`arguments.machine.cores` accepts the cap itself as a score, and the first
version of this offered `arguments.machine.cores` for `twelve`.
`config_internal.hpp`'s `nearest_key()` has both tests already, with the
`edits < closest` half hiding the second one inside the search.

**Three mutations, all caught by the assertion written for them.** `store_fact`
marking the row `Origin::File` — caught by *"the row says which"*. Accepting any
path that walks rather than the one this setting takes — caught by *"including a
real path that is the WRONG fact"*. The clamp overwriting `written` with the
machine's total — caught by *"the file's own 1024TiB survives"*.

**And one thing that did not need building.** All six spellings of `arguments`
work here without this module holding a list of them, because `config.cpp` walks
the real trie: `words_walk.hpp` matches an alias at every segment, so
`args.machine.cores` resolves for exactly the reason it will resolve inside a
program at M10. A string comparison would have needed its own copy of
`words.def`'s five `SAT_ALIAS` rows.

#### And it moved one sentence in §5

§5's finding is that the pool is invisible to every command satl has, and that
stands: nothing in this tree calls `run_over()` except `tests/limits_test`, and
the first real tenant is M10's printer thread. **What moved is the evidence.**
`satl --limits` used to finish with **0** of 24 parked and now finishes with 14
to 19, because the 0.42 ms it spent reading the machine came *before*
`pool::start()` and now does not happen at all — the pool has the whole command
to build in rather than the tail of it.

So §5's *"the pool is never warm while anything is happening"* is no longer true
as written: on `satl --limits` it is two thirds built by the time the command
prints. **The finding is stronger for it, not weaker** — the pool now gets
usefully warm and there is still nothing in the tree that would use it, which is
exactly what §5 says and what M10 is the first milestone able to test.
`src/machine_limits/dump.cpp` and `tests/limits_test/pool.cpp` carry the new
counts beside the old ones.
