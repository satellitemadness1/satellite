# POLYMORPH M6 — user-defined commands written in C++

Written 2026-09-14. **Status: an idea, measured.** The author: "we will have
to work on this together to get all of this actually to work."

## The author's idea

A user defines a command of their own, and its body is C++:

```satellite
their_username.file_op.decompress(path, mode).polymorph()
{
    // a whole C++ file: #includes, int main(args), everything --
    // and a line containing "satellite." runs as satellite
}
```

The interpreter writes that C++ to a file, compiles it with
`std::system("c++ satellite.user_defined.1.cpp -o ...")`, and names the
result after the next free NUMBER it gives the command. From then on,
reaching that number runs that file with the arguments.

## Measured 2026-09-14 — how to run the compiled command

One `display` of `"hello"`, on this machine (24 cores):

| way to run it | per call | 1,000,000 calls |
|---|---|---|
| `std::system("./exe hello")`, a static executable | 1,909 µs | **32 minutes** |
| `std::system("./exe hello")`, a dynamic executable | 2,828 µs | 47 minutes |
| `posix_spawn` of the executable, no shell | 329 µs | 5.5 minutes |
| **compiled library loaded into the running program** (`dlopen`) | **0.02–0.04 µs** | **0.02–0.04 s** |
| a plain function inside the program | 0.02 µs | 0.02 s |
| `satl` today, the whole loop (`for`, the string, `display`) | 5.2 µs | 5.2 s |

- `std::system` starts a shell first, and the shell starts the program. That
  is most of its 1.9 ms.
- **A compiled library is as fast as a built-in function**, and `dlopen`
  worked from a statically linked program like `satl`. The linker warns that
  the machine then needs the same glibc version at run time.
- **Compiling one small command took 0.09 s with `<cstdio>` and 0.92 s with
  `<iostream>`.** That is paid once, then cached.

**Recommended: compile each command to a LIBRARY named by its number, not an
executable.** The author's idea of a file per number stays; the file is a
`.so` instead of a program, and calling it costs a function call instead of
starting a process.

## What has to be designed together

1. **Where the C++ ends.** C++ has `{` and `}` inside strings, comments and
   characters (`'{'`), so counting brackets cannot find the end of the block.
   It needs a closing marker nothing in C++ can contain.
2. **"A line with `satellite.` in it is satellite."** A C++ string or comment
   can contain that text too — `std::cout << "satellite.console"` — and a text
   match like that already misfires once in this tree (ACCESS_PLAN F2). Such
   a line also needs a way to reach the C++ variables around it. Recommended:
   an explicit marker for a satellite line, and the interpreter handing the
   library a small C++ API to run satellite and exchange values.
3. **Values across the wall.** Numbers and strings cross easily. A list, a
   map, a spacesuit or a thread needs a C++ type for the library to receive.
4. **Numbers for user commands.** Language numbers are frozen and never
   reused (WORD_NUMBERS). A user command gets its number under its own root
   (`their_username`), so it can never take one the language will need.
5. **Can a user command replace a language word** such as
   `satellite.console.display`? Recommended: no, only new paths. A program
   that silently changes what `display` does is exactly what DESIGN §1 spends
   the language avoiding.
6. **A machine with no compiler.** The distribute package installs prebuilt
   binaries on machines that may have no `c++`. There the command must fail by
   name, saying a compiler is needed, never crash.
7. **Trust.** Opening someone else's `.satl` compiles and runs their C++ with
   your permissions. That is true of running any program, but it should be
   said, and M27 (the network) must never run one that arrives on the wire.

## Decisions for the author

D1 through D7 above, one per item.
