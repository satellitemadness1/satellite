satellite — what the language is missing to run view_forge
==========================================================
Written 2026-08-23. Subject: /home/madness/code/satl/view_forge, 31 .satl files,
6434 lines, a console program that loads a library of encyclopedia objects out of
a declaration tree and forges one of them onto the screen.

This file is a gap list, not a design argument. Nothing here is a proposal about
what satellite ought to be; every entry is a place where view_forge writes
something and satl currently refuses it. DESIGN.md remains authoritative about
what the language is for, and several entries below are things DESIGN.md has
deliberately never promised — those are marked, because "missing" and "refused on
purpose" are different problems and only one of them is a bug.

METHOD. Every claim was checked by running the interpreter, not by reading it.
The program itself was run first (it dies on line 3), and then each construct it
uses was cut down to a standalone probe and run alone against ./satl. Where an
entry quotes an error, that is the real text satl printed. Where an entry says
something works, a probe proved it works. Counts of affected sites come from grep
over the view_forge tree and are exact as of today.

VERDICT. Nine things block the program. One more is a silent wrong-output bug
that would survive all nine fixes. Everything else view_forge needs — spacesuits,
lists of spacesuits, capsules that hand back lists of spacesuits, methods called
straight off a list element — already works today and needs nothing.


---- THE BLOCKERS, IN THE ORDER THE PROGRAM HITS THEM ----

1. satellite.include CANNOT TAKE A PATH
   Sites: 29 distinct include lines, in 22 of the 31 files.

   view_forge writes:
       satellite.include("object/forge_object.satl")
       satellite.include("../../../object/forge_object.satl")

   satl says:
       satellite.include takes a spaceship name, either bare (my_parser) or
       satellite-rooted (satellite.window)

   This is the first line of the program that fails and it is the whole reason
   nothing else has ever been observed to run. §16 settled the include semantics
   — include-once by canonical path, cycles terminating, bodies first — and all
   of that is fine; the missing piece is only the surface syntax for naming a
   spaceship that is not a sibling file.

   The bare form does not rescue this. Probe: a file in ./object/ named
   forge_object.satl, included from the parent directory as
   satellite.include(forge_object), gives

       cannot find spaceship forge_object (looked in forge_object.satl)

   so the loader looks in the includer's own directory and nowhere below it.
   view_forge is a five-level tree (declarations/objects/countries/china.satl),
   and every one of its includes crosses at least one directory boundary. Two of
   them climb three levels with "../../../".

   What is needed is a decision, not much code: either quoted relative paths
   become legal arguments to satellite.include, or bare names grow a dotted
   subdirectory spelling (satellite.include(object.forge_object)) that the
   loader maps onto directories. The second fits the language's existing dotted
   naming better and keeps paths out of source; the first is what the program
   already assumes. Whichever is chosen, "../.." style upward traversal needs an
   answer of its own, because the declaration files reach back up to the shared
   object definitions rather than down.

2. THERE IS NO LIST LITERAL
   Sites: 1406 as a call argument, plus 18 as an initializer.

   view_forge writes it two ways. As an initializer, inside spacesuit fields:
       satellite.container.list<satellite.variable.string> location_str = {"UNSET", "UNSET"}
       satellite.container.list<satellite.variable.number> links = {0, 0}

   and, far more often, as an argument handed straight into a call:
       local_forge_object.call_set_location({"BERLIN", "OUT_OF_SYSTEM", "GERMANY", "EUROPE"})
       local_forge_object.call_set_links({86, 87, 123, 134})

   satl says, in both positions:
       expected an expression, found Punct({)

   The counts are what matter here. 341 call_set_location, 341 call_set_info,
   341 call_set_affiliations, 341 call_set_links and 42 call_set_type_info — the
   declaration tree is essentially nothing but list literals, and this single
   missing form accounts for more failing lines than every other entry in this
   file combined. A list literal is also the only way the declaration files could
   reasonably be written: the alternative is declaring a named temporary and
   calling .append() four times before every setter, which would roughly triple
   a tree that is already 6434 lines.

   Note this is a genuine hole rather than a refusal. Lists exist, they can be
   declared empty and appended to, and they can be handed around as values; there
   is simply no way to write one down.

3. A LIST ELEMENT CANNOT BE ASSIGNED
   Sites: 5, all inside the setter loops of forge_object and view_type.

   view_forge writes:
       location_str[location_size] = location_input[location_size]

   satl says:
       cannot assign to this expression

   Reading through an index works, including with a variable index and including
   negative indices; only the store side is absent. The evaluator's assignment
   path wants a storage slot and an index expression does not name one.

   This is the one blocker the program could route around on its own — the
   setters overwrite placeholder slots and could instead build a fresh list and
   append — so it is a smaller job than its position here suggests. It is listed
   as a blocker because the code as written stops on it.

4. THERE IS NO WAY TO READ FROM THE KEYBOARD
   Sites: 1, and it is the program's entire reason for existing.

   view_forge writes:
       satellite.console.input("", local_user_input)

   satl says:
       no such module function: satellite.console.input

   satellite.console has display and nothing else. view_forge prompts for the
   name of a target, searches its object library for an exact match, and forges
   what it finds; with no input the program can only ever forge something
   hardcoded.

   Two shapes are possible and the program has already picked one: a capsule that
   takes a prompt and a variable and writes the answer into the variable, which
   means output parameters, which the language does not otherwise have. The other
   shape is satellite.console.input(prompt) handing the line back as a value,
   which needs nothing new from the calling convention. §8.3 already settled that
   a file is a reference type and gave satellite.variable.file a .read(); stdin
   as a satellite.variable.file would make this fall out of machinery that
   already exists, and would be worth weighing before adding a second I/O idea.

5. BARE TRUE AND FALSE ARE NOT LITERALS
   Sites: 35.

   view_forge writes:
       satellite.variable.bool target_list_has_unset = TRUE
       satellite.statement.if(target_found == TRUE)

   satl says:
       unknown variable in capsule: TRUE

   §8.4 gave the language satellite.bool.true and satellite.bool.false as module
   constants and gave the reason, so this one may well be a refusal rather than a
   hole — in which case the fix belongs in view_forge, not here. It is recorded
   because 35 sites is enough that somebody should decide once, deliberately,
   rather than 35 times. If the answer is that satellite.bool.true is the only
   spelling, the error message is the thing to improve: "unknown variable in
   capsule: TRUE" does not tell the reader that satellite.bool.true exists.

6. satellite.statement.else() WITH PARENTHESES
   Sites: 24 — 9 in view_forge_main.satl, 12 in forge_object.satl, 3 in
   view_type.satl.

   view_forge writes:
       satellite.statement.else()
       {

   satl says:
       expected '{' to open a block

   The parser wants bare satellite.statement.else with no parentheses. This is
   pure surface: an else takes no condition, so the empty parens carry no
   meaning and the parser is right to be surprised by them. But view_forge writes
   parens on every other statement form it uses and reached for them here by
   symmetry, which is a fair mistake to make. Accepting an empty pair and
   ignoring it costs one line in the parser; the alternative is to keep refusing
   and say so plainly in the error, which currently mentions only the brace.

7. THERE ARE NO KEYWORD ARGUMENTS, SO NOTHING CAN PRINT WITHOUT A NEWLINE
   Sites: 1, but it is the prompt line.

   view_forge writes:
       satellite.console.display("[SATELLITE_VIEW_FORGE]>>", end="")

   satl says:
       expected ')' to close the argument list

   Two separate absences are tangled here. There is no keyword-argument syntax
   anywhere in the language, and there is no unnewlined print. Only the second
   one actually blocks the program: a prompt that ends in a newline puts the
   cursor on the line below the ">>", which is ugly but survivable, whereas a
   prompt that cannot be written at all is not. A separate capsule —
   satellite.console.write, say — would clear this without opening the much
   larger question of keyword arguments, and would pair naturally with whatever
   answer entry 4 gets.

8. A NAME CANNOT BE DECLARED TWICE IN ONE SCOPE
   Sites: 341 declarations of forge_object local_forge_object and 43 of
   view_type local_view_type, concentrated as 75 in united_states.satl, 66 in
   russia.satl, 60 in imperium.satl, 58 in china.satl, 40 in chaos.satl.

   view_forge writes, over and over inside a single capsule:
       forge_object local_forge_object
       local_forge_object.call_set_object_id(124)
       ...
       germany_object_list.append(local_forge_object)

       forge_object local_forge_object
       local_forge_object.call_set_object_id(125)
       ...

   satl says:
       local_forge_object is already declared in this scope

   The program is using a redeclaration the way C++ would use a fresh block
   scope: build one object, put it in the list, forget the name, build the next.
   Refusing to shadow a live name in the same scope is a defensible rule and
   most languages that allow it regret it. But something has to give at 341
   sites, and there are three ways out worth weighing: allow redeclaration to
   rebind the name outright; give the language a bare nested block { } that opens
   a scope, which is the smallest change and the most conventional; or leave the
   rule alone and let view_forge number its temporaries.

   This one also hides a semantic question that will bite whichever way it goes.
   Whether .append(local_forge_object) stores the object or a reference to it
   decides whether 75 objects built through one name end up as 75 distinct
   entries or 75 views of the last one. §14 made spacesuits reference types, so
   the answer is probably the wrong one for this program, and it will not show up
   as an error — just as a library where every object is the last object.
   Whatever is decided for the redeclaration, this needs a test.

9. A STRING CANNOT BE CONCATENATED WITH A BOOL
   Sites: 0 today. Listed because it is one edit away.

   satl says, for "flag=" + some_bool:
       + does not apply to flag= and true

   string + number coerces and works. string + bool does not. view_forge does not
   currently do it — it writes the words TRUE and FALSE into its literals by hand
   — but the program's whole style is to narrate the value of every variable it
   touches, and the moment somebody narrates a bool the way they narrate a
   number, this fails. Whether the asymmetry is intended is worth confirming.


---- SILENT: WRONG OUTPUT, NO ERROR ----

10. \' INSIDE A DOUBLE-QUOTED STRING IS NOT AN ESCAPE

   view_forge writes:
       satellite.console.display("THE LIBRARY \"target_list\" DOESN\'T CONTAIN UNSET DATA...")

   satl prints:
       DOESN\'T CONTAIN UNSET DATA

   The backslash survives into the output. The string lexer knows \n, \t, \r,
   \\ and \" and passes anything else through untouched, so this never raises an
   error and would still be wrong after every blocker above is fixed. An
   apostrophe needs no escaping inside double quotes, so the program is at fault;
   but a lexer that silently keeps an unknown escape will hide this class of
   mistake forever. Rejecting unknown escapes outright, or accepting \' as a
   redundant spelling of ', both fix it. Doing nothing means it ships.


---- WHAT ALREADY WORKS: DO NOT BUILD THESE ----

Every item here was doubted, probed and confirmed working. They are written down
so that nobody reading the nine blockers above concludes the object model is
missing, because it is not — the object model is the part of this program that
satellite already runs.

  - Spacesuits with satellite.protected and satellite.public blocks, fields,
    methods and a constructor. §14, and it holds up under what view_forge asks.
  - A bare instance declaration with no parentheses — view_forge local_view_forge
    — runs the no-argument constructor. view_forge and forge_object both depend
    on this and both get it.
  - A protected capsule calling another protected capsule of the same spacesuit
    by bare name, which is how every call_* door in forge_object reaches its
    worker.
  - A spacesuit name used as a parameter type: satellite.capsule show(thing t).
    forge_object is passed whole into the forge this way.
  - satellite.container.list<forge_object> — a list whose element type is a
    user-defined spacesuit. This is the spine of the program and it works.
  - A free capsule that hands back a list of spacesuits, and does so with NO
    satellite.returns clause on it. All 25 return_* capsules omit the clause;
    satl infers it and the value arrives intact. Worth knowing, because the
    absence of 25 satellite.returns clauses looks like a blocker and is not.
  - Calling a method straight off a list element: object_list[i].call_get_name_str().
  - Passing a list element straight into a call: call_forge_object(object_list[i]).
  - string + number, with the number coerced. Used on essentially every one of
    the 1019 display lines.
  - .length() and .size() on a string, .length() on a list, .append() on a list,
    .plus() on a number.
  - satellite.main with no explicit satellite.return(satellite) at the end.
    view_forge's main just stops, and that is accepted.
  - satellite.statement.while, satellite.statement.if, == on strings.


---- SUGGESTED ORDER ----

Ordered by what unblocks the most for the least work, not by severity.

  First   2 (list literal) and 1 (include paths). Nothing at all can be observed
          running until the includes resolve, and once they do, the 1406 list
          literals are the next wall. These two together are most of the program.
  Second  8 (redeclaration) with the reference-versus-copy question in it
          settled and tested, then 3 (index assignment). These are what stand
          between "the declaration tree parses" and "the library is correct".
  Third   4 (console input) and 7 (unnewlined print), decided together, since
          both are satellite.console gaining a capsule and both should be weighed
          against §8.3's file type before either is written.
  Last    5, 6, 9 and 10 are each a few lines, and 5 and 6 may be decisions to
          leave the language alone and change view_forge instead. They are
          cheap enough to do at any point but they unblock nothing on their own.

None of this touches DESIGN.md's open ground. §15's bootstrapping stages and
§11's remaining milestones are untouched by everything above; view_forge exercises
the language that already exists and asks it for surface syntax, not for a new
idea about what satellite is.
